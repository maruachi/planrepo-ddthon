# PlanRepo 요구사항

## 1. 제품 목적과 완료 지점

PlanRepo는 SR별 AI-DLC 문서 작성, 질문 응답, 의사결정, 피어 리뷰를 한 작업 맥락에서 처리하는 워크벤치다. 사용자가 문서 전체를 반복해서 읽기 전에 지금 결정해야 할 질문과 이전 검토 이후 바뀐 내용을 확인할 수 있게 한다.

MVP의 완료 지점은 **해당 SR에 적용되는 Inception 및 Construction 설계 산출물의 최신 버전이 승인되어 구현에 인계할 수 있는 상태**다. 완료 상태의 화면 명칭은 `구현 대기`다.

- Construction의 Functional Design, 적용되는 NFR Requirements/NFR Design/Infrastructure Design과 관련 생성 계획·질문을 지원한다.
- 해당 SR에 적용하지 않는 설계 작업은 이유와 판단자를 남겨 `해당 없음`으로 표시한다.
- 코드 생성, Build and Test, PR 리뷰, 병합, 배포는 이 제품의 완료 조건에 포함하지 않는다.
- Code Generation Plan은 구현 인계용 참고 자료로 열람할 수 있지만 설계 산출물과 구분한다.
- Git 브랜치·PR이 없어도 설계 작성과 승인을 완료할 수 있다.
- 피어 리뷰를 Inception·설계 단계로 앞당긴다. 이후 구현·테스트 검증을 대체한다는 의미는 아니다.

## 2. 참조한 실제 질문·답변 흐름

참조 저장소: [table-order-ddthon / aidlc-docs](https://github.com/maruachi/table-order-ddthon/tree/main/aidlc-docs)  
검토한 로컬 원본과 기존 PlanRepo 데이터셋 기준: `a40d56ccedabc5bcd5bbcdf14adc2c4f49110515`.

실제 문서의 흐름을 다음과 같이 모델링한다.

1. AI가 질문을 포함한 생성 계획 Markdown을 작성한다.
2. 사용자는 원문의 선택지 중 답을 고르거나 설명을 작성한다.
3. 답변을 저장하면 해당 문서의 `[Answer]:`에 반영된다.
4. 지정된 결정권자가 답변을 확정한다.
5. 확정 답변을 바탕으로 모호성·모순을 확인한다. 추가 질문이 생기면 같은 실행 맥락에서 2~4를 반복한다.
6. 생성 계획을 검토하고 승인한다.
7. 승인한 생성 계획으로 설계 산출물을 생성한다.
8. 생성된 설계 산출물을 별도로 검토하고 승인한다.
9. 필요한 다음 설계 작업으로 진행한다. 모든 필수 설계가 승인되면 구현 대기로 전환한다.

**답변 저장, 결정 확정, 생성 계획 승인, 설계 산출물 승인은 서로 다른 행동이다.** 질문이 없는 작업은 질문 입력을 생략할 수 있다. 후속 질문은 최초 계획과 기존 답변을 유지한 채 이어진다.

원문의 예:

- `inception/plans/story-generation-plan.md`: 답변 분석 후 계획 승인, 이후 스토리 생성.
- `inception/plans/unit-of-work-plan.md`: 복수 선택 질문 포함.
- `construction/plans/u2-menu-functional-design-clarification-questions.md`: 기존 질문 답변에서 드러난 품절 상품 반환 정책을 추가 질문으로 확인.
- `construction/plans/u2-menu-nfr-design-plan.md`: 열린 질문이 없어 질문 게이트를 생략하는 사례.

### 질문 포맷

- `## Question 1`, `### Q1.`, `### Clarification Question 1` 등의 원본 제목을 지원한다.
- 선택지는 고정 오지선다로 제한하지 않는다. 문서에 있는 선택지 수와 문자(A/B/…/X 등)를 그대로 사용한다.
- 단일 선택, 문서에 명시된 복수 선택, Other와 자유 설명을 지원한다.
- `[Answer]:A`, `[Answer]: A`, `- [Answer]: A`와 답변이 선택지보다 앞에 있는 형식을 보존한다.
- 원본에서 Other가 어떤 문자인지 읽어 사용한다. 항상 X나 마지막 문자라고 추측하지 않는다.
- 기존 `(3)`/`(2)` 표기를 고정 단계 수로 해석하지 않는다. UI에서는 `미확정 질문 3개`, `설계 승인 2/4`처럼 숫자가 뜻하는 대상을 명시한다.
- 질문 번호만으로 답변을 연결하지 않는다. 문서·질문 식별자와 질문 내용/선택지의 변경 여부를 함께 확인한다.

## 3. 범위와 산출물

### 제품 MVP

- 내부 SR 생성 또는 Jira SR 읽기 연결.
- SR별 실행 대상 설계 작업, 필수 산출물, 담당자·결정권자·필수 리뷰어 관리.
- 문서 탐색, Markdown 열람, 질문 추출과 `[Answer]` 반영.
- 결정 제안·확정, 생성 계획 승인, 설계 산출물 승인.
- 문서 버전과 변경 비교, 댓글·수정 요청 및 재검토.
- 내 검토함과 팀 칸반, 차단 원인에서 해결할 항목으로 이동.
- AI 실행·질문 대기·실패·취소·재개 상태 표시.
- 승인된 문서 버전과 확정 답변을 묶은 구현 인계 컨텍스트.

### 이번 HTML 목업

- 위 흐름을 비교할 수 있는 서로 다른 화면 구성 4종.
- 외부 라이브러리·서버 없이 여는 독립 HTML 파일.
- 선택, 탭 전환, 답변 저장/확정, 버전 확인/승인 등의 프런트엔드 예시 상호작용.
- SR·사용자·승인 기록은 예시이며 실제 Jira/GitHub/AI와 연결하지 않는다.
- 실제 인증·권한 검증, 공동 저장, 동시 편집, AI 실행, Git 쓰기는 구현 범위가 아니다.
- 데모 상태는 새로고침 시 초기화됨을 화면에 표시한다.

## 4. 단계와 상태

칸반은 업무 진행 위치를 표시한다.

`SR 접수 → Inception → Construction 설계 → 구현 대기`

각 칸반 카드에는 다음 세 가지를 분리해서 표시한다.

| 구분 | 예시 |
|---|---|
| 진행 위치 | Inception / 요구사항 분석, Construction / U2 Functional Design |
| 검토 상태 | 답변 필요, 결정 확정 대기, 계획 승인 대기, 수정 중, 수정 확인 대기, 산출물 승인 대기, 승인 완료 |
| AI 실행 상태 | 실행 전, 실행 중, 추가 답변 대기, 초안 준비, 실패, 취소, 중단·재개 가능 |

리뷰 요청 때문에 SR을 별도 Review 단계로 이동하지 않는다. 팀이 강제할 리뷰 시점은 단계별 필수 승인 조건으로 관리한다. 수시 의견 요청도 허용한다.

문서 탐색에서 다른 단계를 클릭하는 행동과 실제 단계 전환을 구분한다. 단계 전환 버튼은 `Construction 설계 시작`, `설계 승인 완료`처럼 결과를 설명한다. 드래그를 제공할 경우에도 단계 전환 조건을 동일하게 검사한다.

진행률의 분모는 해당 SR의 실행 대상 작업·필수 산출물이다. 생략한 단계를 미완료로 세지 않는다. 여러 유닛의 설계가 병렬로 진행될 때 각 유닛의 진행 위치와 미해결 의존성을 표시한다.

## 5. 역할과 승인 정책

| 역할 | 주요 행동 |
|---|---|
| 요청자·기획자 | 요구사항 보완, 범위·수용 기준 검토 |
| 개발자·문서 작성자 | 답변 제안, 문서 수정, 수정 완료 제출, AI 실행 |
| 결정권자 | 담당 질문의 답변 확정·변경 결정과 근거 기록 |
| 리뷰어 | 특정 버전 검토·승인, 수정 요청, 수정 결과 확인 |
| 리더 | SR 필수 리뷰어·작업 범위 설정, 예외 진행 판단 |

MVP는 SR별 지정한 필수 리뷰어 전원 승인을 기본 정책으로 한다. 과반수·리더 승인 등을 제공하는 경우 요청에 적용된 정책과 리뷰어 집합도 기록한다. 정책을 바꿔 과거 승인이 자동으로 최신 정책의 승인이 되지 않게 한다.

수정 요청의 최종 확인은 요청한 리뷰어가 수행한다. 수정 완료 제출자와 최종 확인자를 구분한다. 리뷰어 변경·위임이 필요한 경우 변경자와 이유를 남긴다.

## 6. 질문과 결정

### 상태

`미답변 → 편집 중/미저장 → 답변 제안(저장됨) → 확정`

확정된 답변을 수정하면 새로운 제안으로 돌아가고 재확정이 필요하다. 이전 확정 기록은 삭제하지 않는다.

### 질문 카드 필수 정보

- 질문과 원문 위치, 포함된 문서 버전.
- 선택지와 자유 설명, 현재 `[Answer]`.
- 결정해야 하는 이유, 관련 결정·문서 링크.
- 선택의 영향과 근거가 있을 때 해당 정보. AI 권고는 사람의 확정과 구분하고 출처가 없으면 확정 사실처럼 쓰지 않는다.
- 담당 결정권자, 필수 여부, 해결해야 할 단계.
- 제안/확정 상태, 확정자·시각·근거.
- 추가 질문이면 최초 질문 또는 부모 실행으로 돌아가는 링크.

현재 단계의 필수 질문만 단계 진행을 차단한다. 일반 의견, 선택 질문, 이후 단계에서 정하기로 한 사항은 차단 여부를 별도로 표시한다.

일괄 답변 반영은 대상 문서와 질문 목록을 미리 보여준다. 저장이 실패하면 성공한 것처럼 표시하지 않는다. 질문 형식 오류·중복 번호·Answer 누락은 해당 위치를 안내하며 미답변 0건으로 숨기지 않는다.

## 7. 문서 버전·리뷰·수정 요청

### 버전 원칙

- 승인 요청은 `문서 ID + 문서 버전`에 고정한다.
- 본문 또는 Answer 변경은 새 버전을 만든다. 기존 승인본과 승인자·시각은 보존한다.
- 새 버전은 재승인이 필요하며, 이전 승인을 그대로 승계하지 않는다.
- 리뷰어가 v2를 확인한 후 v3가 생성됐다면, v2 화면의 승인으로 v3를 승인할 수 없다.
- 댓글에는 원래 버전과 인용 문구·위치를 저장한다. 새 버전에 위치를 찾지 못하면 `이전 버전의 댓글`로 표시한다.
- 원본 계획이 바뀌면 그 계획을 입력으로 사용한 산출물과 후속 산출물에 재검토 필요를 표시한다. 같은 단계의 산출물도 대상이다.
- 입력 변경 때문에 기존 산출물을 자동 삭제하거나 모든 업무를 이전 단계로 되돌리지는 않는다.

### 리뷰 화면 순서

1. 이번 리뷰에서 필요한 판단과 변경 요약.
2. 이전 승인본 또는 선택한 과거 버전과 변경 비교.
3. 관련 질문·확정 답변·열린 수정 요청.
4. 전체 원문과 버전 이력.
5. 체크리스트, 필수 리뷰어 상태, 현재 버전 승인.

검토함의 요청 제목만 보고 즉시 승인하는 버튼은 제공하지 않는다. 승인 패널에서 해당 버전의 변경 내용을 확인한 뒤 승인한다.

### 수정 요청 상태

`열림 → 수정 완료·확인 대기 → 리뷰어 확인 완료`

- 작성자는 수정한 새 버전을 지정해서 수정 완료를 제출한다.
- 수정 완료 제출만으로 차단이 해제되지 않는다.
- 리뷰어는 지정된 수정 버전을 확인하고 해결하거나 다시 연다.
- 확인 대기 중 문서가 다시 바뀌면 최신 수정 버전을 재확인해야 한다.
- AI가 수정 초안을 별도 문서로 만들었으면 원본의 새 버전으로 반영하는 명시적 행동을 거친다. 별도 초안 생성만으로 원본 수정 요청을 해결하지 않는다.

## 8. AI 실행과 재개

실행별로 SR, 실행 ID, 부모 실행 ID, 작업 종류, 입력 문서 버전, 확정 답변, 수정 요청, 시작·완료 시각, 체크포인트를 기록한다.

- 미저장 답변으로 실행하지 않는다. 해당 작업의 필수 답변이 확정되어야 한다.
- 질문 분석과 생성 계획 승인, 산출물 생성을 구분한다.
- 생성 계획 승인이 필요한 작업은 해당 계획 승인 후 산출물을 생성한다.
- 수정 요청을 반영하는 실행은 열린 수정 요청이 있어도 시작할 수 있다. 수정 요청 때문에 수정 실행 자체가 막히는 교착을 만들지 않는다.
- 결과는 새 초안이다. 생성 성공이 곧 승인이나 다음 단계 이동을 뜻하지 않는다.
- 추가 질문을 받으면 최초 계획·기존 답변·실행 ID를 보존하고 새 답변을 추가하여 이어서 실행한다.
- 실패·취소·연결 중단 시 기존 문서와 확정 답변을 보존한다. 부분 결과는 승인 가능한 최종 산출물로 취급하지 않는다.
- 동일 실행 중복 시작을 막는다. 재시도는 재시도 대상과 사용할 입력 버전을 보여준다.
- 실행 중 입력이 바뀌면 이전 입력의 결과가 최신 문서를 덮어쓰지 않는다. 이전 입력 기준 초안으로 표시하고 재검토/재실행을 안내한다.
- 브라우저나 CLI 재시작 후 마지막 체크포인트와 필요한 다음 행동으로 복귀한다.

## 9. 서로 다른 세 가지 게이트

| 행동 | 필수 조건 |
|---|---|
| AI 실행 | 해당 작업의 입력 저장 완료, 필수 답변 확정, 작업에 필요한 생성 계획 승인, 중복 실행 없음 |
| 문서 승인 | 확인한 버전 일치, 해당 버전의 필수 답변 확정, 차단 수정 요청 해결, 검토 체크리스트 확인 |
| 다음 단계·구현 인계 | 해당 단계 필수 산출물의 유효한 최신 승인, 필수 결정 완료, 차단 요청 없음, 입력 변경 영향 해소, 진행 중/미해결 실행 없음 |

리더의 예외 진행을 제공하는 경우 미충족 조건·사유·실행자를 남기고 `예외 진행`으로 표시한다. 미결정이나 미승인을 완료로 바꾸지 않는다.

## 10. UI/UX 요구사항

### 내 검토함

- 개인 기본 화면으로 제공한다. 팀 전체 진행은 별도 Board로 접근한다.
- 답변 작성, 결정 확정, 계획 승인, 산출물 승인, 수정 결과 확인을 구별한다.
- 기한 초과 → 차단 항목 → 직접 요청·멘션 → 생성 시각 순으로 정렬한다.
- 각 행에서 SR, 요청 종류, 대상 문서·버전, 요청자, 기한, 다음 행동을 확인한다.
- 아무 항목이 없는 경우와 필터 때문에 결과가 없는 경우를 구별한다.

### 팀 보드

- 카드에 대표 차단 원인, 해결 담당자, 대기 기간을 우선 표시한다.
- 모든 경고 배지를 동등하게 나열하지 않는다. 추가 항목은 상세로 연다.
- 차단 원인을 누르면 해당 질문·문서·수정 요청으로 이동한다.
- 이동 전에 통과 조건을 보여주고 바로 해결할 행동을 제공한다.
- Git/PR 상태는 선택적 참고 정보이며 카드의 핵심 진행 상태와 혼합하지 않는다.

### SR 상세

- 상단에 SR, 현재 작업, 지금 필요한 행동, 담당자, 차단 이유를 고정한다.
- 중앙은 질문과 변경 검토에 집중한다. 문서 트리·팀 정보·AI 실행·Git 정보는 접을 수 있는 보조 영역으로 제공한다.
- 문서 집중 보기와 패널 폭 조절을 지원한다. 좁은 화면에서는 패널을 서랍 또는 순차 보기로 바꾼다.
- 주요 버튼은 `답변 저장`, `결정 확정`, `생성 계획 승인`, `설계 초안 검토`, `설계 승인 완료`처럼 결과를 설명한다.
- 실행 상태를 보려면 반드시 터미널을 열어야 하는 구조를 피한다. 답변 대기·실패·재개 행동은 본문에도 표시한다.
- 상태를 색만으로 전달하지 않는다. 텍스트·아이콘·숫자를 함께 사용한다.
- 키보드 초점, 라디오/체크박스 선택, 버튼 비활성 사유, 읽기 가능한 글자 크기를 제공한다.
- 자동 저장/저장 중/저장 실패/미저장 표시, 불러오기/빈 상태/연결 오류를 정의한다.

## 11. 핵심 데이터 연결

| 대상 | 반드시 연결할 정보 |
|---|---|
| SR | 담당자, 업무 단계, 작업 범위, 적용 워크플로우 버전, 관련 Jira/저장소 |
| 설계 작업/유닛 | 적용 여부·사유, 필수 산출물, 선행 작업, 검토 시점 |
| 문서 버전 | 원문, 종류, 문서 ID, 버전, 생성 근거, 입력 문서 버전, 이전 버전 |
| 결정 | 원본 질문/선택지, 답변, 필수 여부, 결정권자, 확정 버전·시각·근거 |

| AI 실행 | 최초/부모 실행, 입력 묶음, 출력 버전, 실행 상태, 체크포인트, 오류 |

## 12. 인수 시나리오

1. 원문의 선택지 문자와 줄바꿈 형식을 유지하고 지정된 Answer만 바뀐다.
2. 답변을 저장해도 결정 확정·문서 승인이 자동으로 완료되지 않는다.
3. 후속 질문에 답한 뒤 기존 계획과 이전 답변을 유지하고 실행을 이어간다.
4. v2 승인 뒤 v3가 만들어지면 v2 이력은 남고 v3에는 재승인이 필요하다.
5. 과거 버전 화면에서 최신 버전을 승인할 수 없다.
6. 수정 완료 제출 후 리뷰어 확인 전에는 차단이 유지된다.
7. 수정 요청이 있어도 해당 수정 초안 생성은 가능하다.
8. 원본 변경 시 같은 단계/다음 단계의 관련 산출물에 재검토 필요가 표시된다.
9. 실행 실패·취소·새로고침 이후 실제 제품은 저장된 입력과 체크포인트로 복구한다.
10. 실행 중 입력 변경이나 중복 클릭으로 기존 문서가 덮어써지지 않는다.
11. Construction의 적용 설계 산출물이 승인되면 Git/PR 없이 구현 대기가 된다.
12. 질문 형식 오류와 미답변 없음이 구별되며 오류 수정 후 차단이 해제된다.

## 13. 재검토 결과와 구현 전 남은 항목

이번 개정에서 지원 범위, 질문 반복 흐름, 버전 승인, 수정 확인, 실행 복구, UI 우선순위의 모순은 요구사항으로 정리했다. 추가로 발견한 후속 질문 문맥 유실, 생성 초안의 원본 반영, 의존 산출물 재검토 전파, 완료 후 차단 재발, 파서 오류 표시도 위 규칙에 반영했다.

HTML 목업만으로 아래 실제 제품 기능까지 완성된 것은 아니다. AI-DLC 연동 구현 단계의 별도 과제로 남긴다.

- SR별 적용 워크플로우 버전과 산출물 매핑의 실제 설정.
- Markdown/Workbench 메타데이터의 저장 원본, 동시 변경 충돌 처리 및 복구 방식.
- 로그인과 서버의 실제 역할·승인 권한 검사, 팀 공유 저장.
- Jira 읽기·Git 입출력 연결 및 동기화 오류 처리.
- AI-DLC/CLI 실행 어댑터, 실행 이벤트·상태·체크포인트의 실제 연결.
- 기한·알림 채널, 리뷰어 부재 시 위임 정책의 운영 설정.

목업의 우선 목적은 실제 연동 전 **어떤 정보 배치가 질문 응답과 변경 검토를 가장 빠르게 만드는지 비교하는 것**이다.
