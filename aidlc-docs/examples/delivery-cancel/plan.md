# Inception Plan: [예시] 배송 전 주문 취소·환불

## 요구사항

이 문서는 PlanRepo의 문서 리뷰·결재를 체험하기 위한 예시 Plan입니다. 실제 고객 주문이나 결제를 실행하지 않습니다.

확인된 요구사항(사용자 초안 및 답변 기준):

- 고객센터를 기다리지 않고 고객이 주문 상세에서 직접 주문 전체를 취소할 수 있게 합니다.
- 배송 전 전체 주문만 직접 취소하며, 취소 확정 직전에 배송 상태를 다시 확인합니다.
- 이미 배송이 시작됐다면 주문을 유지하고 자동 환불 없이 반품 방법을 안내합니다.
- 일부 상품만 취소하는 경우는 이번 범위에서 제외하고 고객센터로 안내합니다.
- 취소 요청 버튼을 반복해서 눌러도 주문 취소와 환불 요청은 한 번만 처리해야 합니다.
- 주문 취소 완료와 환불 완료는 다릅니다. 환불 접수, 환불 상태 확인 중, 환불 완료를 구분해 보여 줍니다.
- 환불 서비스 응답이 늦으면 '환불 상태 확인 중'으로 안내하고, 30분 안에 확인되지 않으면 담당자에게 알려 확인합니다.
- 환불 금액은 실제 결제 금액 기준입니다. 예시 주문은 상품 45,000원 - 할인 9,000원 + 배송비 3,000원 = 환불 접수 39,000원입니다.
- 환불은 기존 결제 수단으로 요청하며 통상 3~5영업일이 걸릴 수 있다는 안내를 표시합니다.

범위에서 제외(확인됨): 쿠폰 재발급, 부분 취소 금액 계산, 배송 후 실제 반품 처리, 실제 결제 실행은 이번 Plan의 범위에 포함하지 않습니다.

필요한 화면(확인됨): 주문 상세 화면, 취소 확인 화면, 취소 결과와 환불 상태 화면.

### 읽는 사람이 먼저 알아야 할 것

이 예시의 고객은 주문한 머그컵을 받기 전에 주문 전체를 취소하려고 합니다. 고객에게 중요한 것은 세 가지입니다. 지금 취소할 수 있는지, 얼마가 돌아오는지, 실제 환불이 끝났는지입니다.

사람은 취소가 허용되는 범위와 예외를 결정합니다. AI는 그 결정을 문서와 화면 예시로 정리합니다. 문단 번호를 연결하거나 이미 적힌 내용을 별도의 근거 칸에 다시 옮겨 적을 필요는 없습니다.

### 잘 만들었다고 판단할 기준

| 확인하는 상황 | 기대하는 결과 |
|---|---|
| 배송 전 주문 전체를 취소합니다. | 주문은 취소 완료가 되고 39,000원 환불 접수를 안내합니다. |
| 취소를 확정하기 전에 배송이 시작됐습니다. | 주문을 유지하고 반품 방법을 안내합니다. 자동 환불하지 않습니다. |
| 취소가 먼저 확정됐습니다. | 나중에 들어온 배송 시작 처리로 취소 완료가 뒤집히지 않습니다. |
| 같은 취소 버튼을 여러 번 누릅니다. | 주문 취소와 환불 접수는 각각 한 번만 처리됩니다. |
| 환불 응답을 아직 받지 못했습니다. | 환불 완료라고 표시하지 않고 확인 중이라고 안내합니다. |
| 주문 중 일부 상품만 취소하려고 합니다. | 직접 취소하지 않고 고객센터 이용을 안내합니다. |

## 사용자 시나리오

**상황 1 — 배송 전 전체 취소 성공(확인됨):** 고객이 주문 상세에서 취소를 요청합니다. 취소 확인 화면에서 환불 접수 39,000원과 기존 결제 수단, 통상 3~5영업일 안내를 확인하고 취소를 확정합니다. 취소 확정 직전에 배송 상태를 다시 확인해 배송 전이면 취소를 완료하고 환불 접수 상태로 전환합니다.

**상황 2 — 취소 확정과 배송 시작의 경합(확인됨, 답변 기준):** 고객이 취소를 확정하려는 순간 배송이 시작되어 두 처리가 겹치는 경우, 취소 확정 직전 배송 상태를 재확인해 배송 시작이 확인되면 배송을 우선합니다. 주문은 유지하고 취소·환불은 실행하지 않으며 반품 안내로 전환합니다. 배송 전 상태에서 취소 확정이 먼저 완료되면 취소 완료 상태를 유지하고 배송 시작 처리는 거절합니다. 두 상태 변경은 같은 주문에 대해 한 번만 확정되도록 합니다.

**상황 3 — 일부 상품만 취소(확인됨, 범위 밖):** 일부 상품만 취소하려는 경우는 이번 범위에서 제외하고 고객센터로 안내합니다.

**상황 4 — 환불 응답 지연(확인됨):** 환불 서비스 응답이 늦으면 '환불 상태 확인 중'으로 안내하고, 30분 안에 확인되지 않으면 담당자에게 알려 확인합니다. 환불 접수, 환불 상태 확인 중, 환불 완료를 구분해 보여 줍니다.


### 고객에게 보여줄 화면 문구

**배송 전 전체 취소 성공**

- 상태: 주문 취소 완료 · 환불 접수
- 제목: 주문을 취소했어요
- 설명: 환불 39,000원을 접수했어요. 결제했던 수단으로 돌려드리며 통상 3~5영업일이 걸릴 수 있어요.
- 버튼: 주문 상세로

**취소·배송 시작 경합**

- 상태: 배송 중 · 주문 유지
- 제목: 이미 배송이 시작됐어요
- 설명: 지금은 주문을 취소할 수 없어요. 상품을 받은 뒤 반품 방법을 확인해 주세요. 자동 환불은 진행하지 않았어요.
- 버튼: 반품 방법 보기

**일부 상품만 취소**

- 상태: 주문 유지
- 제목: 일부 상품만 취소하려면
- 설명: 일부 상품 취소는 고객센터에서 도와드려요. 현재 주문은 그대로 유지돼요.
- 버튼: 고객센터 안내

**환불 응답 지연**

- 상태: 취소 완료 · 환불 확인 중
- 제목: 환불 상태를 확인하고 있어요
- 설명: 주문 취소는 완료됐고 환불 결과를 확인하고 있어요. 환불을 다시 요청하지 않으셔도 돼요. 30분 안에 확인되지 않으면 담당자가 확인해요.
- 버튼: 주문 상세로

화면 문구는 이 Plan에서 검토할 제안입니다. 실제 고객 화면의 캡처가 아닙니다.

## 진행 계획

이 예시는 새 기능의 개발 전에 팀이 같은 문서를 읽고 동의하는 과정까지 진행합니다.

1. **초안을 올립니다.** 기획 담당자가 가지고 있던 설명을 그대로 올립니다. 올린 문서가 바로 Plan이 됩니다.
2. **필요한 부분만 다듬습니다.** 기획 담당자는 문서를 직접 수정할 수 있습니다. AI에게 요약, 빠진 질문, 문장 수정이나 화면 예시를 요청하는 것은 선택입니다.
3. **중요한 선택을 확인합니다.** 이 예시에서는 취소와 배송 시작이 겹칠 때 먼저 확정된 주문 상태를 유지하기로 정했습니다.
4. **동료 검토자 한 명에게 검토받는 것을 목표로 합니다.** 검토자는 고객에게 보여줄 내용과 예외 처리가 문서에 맞는지 읽고, 바꿔야 할 문단에 의견을 남깁니다.
5. **수정한 문서를 다시 확인합니다.** 작성자는 의견을 반영합니다. 시스템은 새 버전과 변경 내용을 연결합니다.
6. **문서를 승인합니다.** 검토자가 현재 문서를 승인하고 담당자가 승인 범위를 확정합니다. 이 승인은 문서의 내용에 대한 합의입니다.

AI 질문에 전부 답하거나 별도의 근거 기록을 작성하는 일은 승인 조건이 아닙니다. 사람이 리뷰에서 요청한 필수 수정은 해결 여부를 확인합니다.

이번에 확정하지 않는 일은 실제 개발 착수, 배포 일정, 실제 결제나 환불 실행입니다. 이 문서는 그 단계에서 활용할 계획입니다.

## 주요 구조

구성요소는 고객 화면, 주문 취소 API, 주문 상태 저장소, 배송 상태 조회, 환불 서비스입니다.

각 부분은 다음 순서로 연결됩니다.

- 고객 화면 → 주문 취소 API: 고객이 주문 상세에서 취소를 요청하면 취소 처리를 호출합니다.
- 주문 취소 API → 배송 상태 조회: 취소 확정 직전에 배송 상태를 다시 확인합니다.
- 주문 취소 API → 주문 상태 저장소: 취소 완료 상태를 기록하고 두 상태 변경이 한 번만 확정되도록 합니다.
- 주문 취소 API → 환불 서비스: 배송 전 취소가 확정되면 환불 접수를 요청합니다.
- 환불 서비스 → 고객 화면: 환불 접수, 환불 상태 확인 중, 환불 완료 상태를 구분해 표시합니다.

### 각 부분을 쉬운 말로 보면

| 부분 | 하는 일 |
|---|---|
| 고객 화면 | 취소 버튼과 취소·환불 상태를 보여 줍니다. |
| 주문 취소 API | 화면에서 받은 취소 요청을 처리하는 서버 창구입니다. |
| 주문 상태 저장소 | 주문이 배송 전인지, 배송 중인지, 취소됐는지 기록합니다. |
| 배송 상태 조회 | 취소를 확정해도 되는지 배송의 최신 상태를 확인합니다. |
| 환불 서비스 | 결제했던 수단으로 환불을 접수하고 처리 상태를 알려 줍니다. |

개발 단계에서 정할 내용: 저장 방식과 서비스 사이의 자세한 데이터 형식은 이 문서의 고객 약속을 지키는 방향으로 정합니다.

## 주요 결정

**결정: 먼저 확정된 주문 상태를 유지합니다.** SR 담당자가 답한 내용에 따라, 취소 확정 직전 배송 상태를 재확인해 배송 시작이 확인되면 배송을 우선합니다. 주문은 유지하고 취소·환불은 실행하지 않으며 반품 안내로 전환합니다. 배송 전 상태에서 취소 확정이 먼저 완료되면 취소 완료 상태를 유지하고 배송 시작 처리는 거절합니다. 두 상태 변경은 같은 주문에 대해 한 번만 확정되도록 합니다. 이는 예시 체험용 결정이며 실제 서비스 정책의 확정이 아닙니다.

**결정: 버튼을 여러 번 눌러도 한 번만 처리합니다.** 취소 요청 버튼을 반복해서 눌러도 주문 취소와 환불 요청은 한 번만 처리합니다.

**결정(확인됨): 환불 상태 구분과 지연 처리.** 환불 접수, 환불 상태 확인 중, 환불 완료를 구분해 보여 주고, 응답 지연 시 30분 기준으로 담당자에게 알립니다.

개발 전에 더 구체화할 내용: 반품 안내로 연결할 실제 주소, 운영 담당자에게 알리는 채널, 주문 상태를 한 번만 확정하는 저장 방식은 구현 준비에서 정합니다. 이번 문서 승인으로 이 세부 사항까지 정했다고 보지 않습니다.

## 작업 단위

- 작업 단위 1: 주문 상세·취소 확인·취소 결과/환불 상태 화면 구성(고객 화면).
- 작업 단위 2: 주문 취소 API의 취소 확정 직전 배송 상태 재확인과 먼저 확정된 주문 상태를 유지하는 처리.
- 작업 단위 3: 주문 상태 저장소의 취소 완료/배송 시작 단일 확정과 반복 요청을 한 번만 처리하는 기능.
- 작업 단위 4: 환불 서비스 연동과 환불 접수·확인 중·완료 상태 표시 및 39,000원 예시 금액 표기.
- 작업 단위 5: 환불 응답 지연 시 '환불 상태 확인 중' 안내와 30분 기준 담당자 알림.

각 작업은 고객에게 약속한 동작을 기준으로 나눴습니다. 세부 코드·저장 기술·배포 작업은 다음 개발 과정에서 정합니다.
