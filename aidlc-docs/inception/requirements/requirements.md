# PlanRepo 요구사항 명세

상태: 사용자 승인 완료. requirements-approval-questions.md의 A 답변을 2026-09-08T11:47:05Z에 확인했다.

## 1. 의도 분석

- 사용자 요청: AI-DLC의 구현 전 계획 문서 생성·진행·검토를 하나의 UI에서 수행하고 Git 의존성을 분리하는 PlanRepo 개발. 이번 요청은 첫 미완료 항목부터 작업 재개.
- 요청 유형: New Project / Greenfield.
- 범위: System-wide. SR 칸반, 계획 워크플로우, CLI 연동, 문서 버전 관리, 피어 리뷰를 포함하는 로컬 웹 앱.
- 복잡성: Moderate. 실제 CLI 실행 및 문서·의사결정 이력의 일관성이 주요 설계 과제.
- 분석 깊이: Standard. 하루 내 개발할 MVP이며 운영 서비스 품질이나 다중 사용자 배포를 목표로 하지 않는다.
- 목표 사용자: 로컬에서 SR 계획을 작성하는 개발자. 피어 리뷰는 동일 앱에서 작성자·리뷰어 역할을 바꿔 시연한다.

## 2. 근거와 답변 해석

원문은 [제품 요구사항](../../../requirements/planrepo-requirements.md), 구체적 범위는 [기존 질문 Q1–Q13](requirement-verification-questions.md)과 [추가 질문 C1](requirements-clarification-questions.md)에 근거한다. 검증 결과는 [답변 검증 기록](requirement-answer-validation.md)에 기록한다.

상세한 사용자 설명을 선택 문자보다 우선한다. Q6의 B에도 불구하고 명시한 비교·복원을 MVP에 포함한다. Q7 C에 따라 Peer Review는 독립된 칸반 열이 아닌 카드의 별도 상태이다. Q10 A는 검증 범위를 정하며, Q1·Q5·Q6의 실제 저장 및 이력 요구를 제거하지 않는다.

C1 A로 로컬 macOS의 Claude Code CLI와 기존 인증 사용이 정해졌다. 이는 실행 환경 선택에 대한 답변이다. CLI 설치 상태, 인증 유효성 및 호출 성공을 실제로 검증한 것은 아니다.

## 3. 제품 경계

PlanRepo가 관리하는 AI-DLC 과정은 SR의 요구사항 분석부터 Inception·Construction의 코드 구현 직전 계획 문서까지이다. 코드 생성·빌드·실행, 커밋·PR 작성은 개발자가 외부에서 수행한다. PlanRepo 자체를 개발하기 위해 수행하는 이 저장소의 AI-DLC Construction 단계와 제품의 기능 범위를 구분한다.

첫 버전에 포함하는 범위는 직접 SR 생성, 계획 생성·진행, 문서 열람·편집·이력·비교·복원, 사람의 결정 기록, 진행을 막지 않는 리뷰, 수동 구현 완료 표시이다. Jira는 향후 연결할 수 있는 인터페이스 골격까지만 포함한다.

실제 Jira 가져오기·동기화, Git 읽기·쓰기·문서 동기화, 자동 PR 생성, 사용자 로그인·팀별 권한, 실제 다중 사용자 협업, 운영 배포 및 고가용성은 이번 범위에 포함하지 않는다.

## 4. 기능 요구사항과 수용 기준

### FR-01. SR 직접 생성과 조회

근거: 원문, Q1 B, Q2 A 및 상세 설명.

제목과 요구 설명을 필수로 입력하고 마크다운 문서를 선택적으로 첨부하여 SR을 생성한다. 생성된 SR은 자체 저장소에 보관되고 SR 목록에 표시된다. SR 상세 화면에서 입력 내용과 연결된 계획 문서를 확인한다.

수용 기준: 필수 입력을 제공하면 SR 카드가 생성된다. 필수값이 비어 있으면 생성되지 않고 이유를 표시한다. 첨부 유무 모두 지원하며 첨부 내용은 해당 SR의 생성 문맥으로 사용할 수 있다.

### FR-02. 칸반 단계와 회차 표시

근거: 원문, Q3 B, Q7 C, Q8 A.

칸반은 SR 목록, 요구사항 분석, Inception, Construction, 구현 대기, 구현 완료의 고정 열을 가진다. Inception과 Construction 카드 숫자는 각 단계의 반복 진행 회차이다. 회차마다 새 열을 추가하지 않는다. 리뷰 상태는 진행 단계와 별도로 표시한다.

수용 기준: 하나의 SR을 선택해 각 계획 단계의 위치를 확인할 수 있다. 같은 단계에서 반복 진행하면 해당 카드에서 회차 변화를 확인할 수 있다. 숫자가 완료한 하위 stage 수를 뜻하지 않도록 표시한다.

회차의 시작값·증가 시점과 하위 stage에서 상위 칸반 열로의 정확한 매핑은 설계에서 정의한다.

### FR-03. 실제 CLI를 통한 계획 문서 생성

근거: Q1 B, Q4 C, C1 A.

사용자가 다음 단계 진행을 요청하면 서버는 로컬 macOS의 Claude Code CLI를 실행·연결하고, AI-DLC 규칙과 해당 SR의 요구사항·기존 문서·관련 결정을 문맥으로 전달하여 계획 문서를 생성한다. 기존 로컬 인증을 사용한다. 문서 생성 결과는 해당 SR에 연결해 저장한다.

수용 기준: 적어도 한 번의 실제 CLI 실행으로 생성한 문서를 UI에서 열람하고 저장할 수 있다. 실행 전·진행 중·성공·실패를 구분할 수 있다. CLI 실행 실패를 생성 성공으로 표시하지 않는다. 제품의 문서 생성 경로가 코드 구현을 자동 실행하지 않도록 범위를 제한한다.

### FR-04. AI-DLC 단계 진행과 사람의 결정

근거: 원문, Q4 C, Q6 상세 설명, Q8 A.

SR의 계획 단계, 생성 문서 및 필요한 사용자 입력을 단일 UI에서 확인한다. AI-DLC에서 질문이나 승인·수정 요청이 필요한 경우 사용자의 응답을 기록하고 후속 진행의 문맥으로 사용한다. 피어 리뷰의 비차단 정책과 AI-DLC 자체의 단계 승인 조건은 구분한다.

수용 기준: 생성 문서를 검토한 사용자의 결정 또는 수정 요청이 이력에 남고, 다음 진행에서 참조할 수 있다. 코드 구현 직전까지 계획을 마치면 구현 대기 상태로 이동할 수 있다.

### FR-05. Git에 독립적인 저장

근거: Q1 B, Q5 상세 설명, Q6 상세 설명.

SR, 계획 문서, 진행 정보, 문서 버전 및 사람의 결정·수정 요청 이력은 PlanRepo가 자체 관리한다. 계획 작업에 Git 저장소 연결이나 커밋을 요구하지 않는다.

수용 기준: Git을 연결하지 않은 상태에서 SR 생성, 문서 생성·수정 및 이력 조회가 가능하다. 저장된 내용은 이후 다시 열어 확인할 수 있다. 저장 기술과 데이터 위치는 설계에서 결정한다.

### FR-06. 문서 편집·버전 이력·비교·복원

근거: Q6 상세 설명.

UI에서 생성 문서를 읽고 수정한다. AI-DLC의 생성·진행과 사람의 편집·의사결정·수정 요청을 각각 이력으로 남긴다. 이전 버전을 열람하고 두 버전의 차이를 확인하며 이전 내용으로 복원할 수 있다. 본문을 바꾸지 않는 결정도 기록에서 누락하지 않는다.

수용 기준: AI 생성, 사람의 편집, 수정 요청 및 의사결정을 각각 수행한 뒤 사건과 관련 문서 버전을 식별할 수 있다. 이전 내용과 현재 내용을 비교하고 복원할 수 있으며 기존 이력이 사라지지 않는다.

검토용 설계 원칙: 복원은 과거 이력을 덮어쓰지 않고 새 버전으로 남긴다. 결정 이력은 대상 문서 버전과 연결하고 본문 변경이 없어도 별도 사건으로 기록한다. 구체적인 데이터 모델은 이후 설계에서 확정한다.

### FR-07. 진행을 막지 않는 피어 리뷰

근거: 원문, Q7 C, Q9 A, Q6 상세 설명.

Inception 또는 Construction에서 원하는 시점에 리뷰를 요청한다. SR은 기존 열을 유지하고 리뷰 상태를 별도로 표시하며, 리뷰가 끝나지 않아도 작성자는 다음 단계로 진행할 수 있다. 로컬에서 작성자·리뷰어 역할을 바꿔 검토와 피드백을 시연한다.

수용 기준: 리뷰 요청 전후로 카드의 계획 단계가 유지된다. 리뷰 진행 중에도 다음 단계 진행을 사용할 수 있다. 검토 결과나 수정 요청을 기록하고 그 대상 문서 버전을 확인할 수 있다. 리뷰가 이후 수정된 문서까지 승인한 것으로 잘못 표시되지 않도록 대상 버전을 구분한다.

리뷰 상태명과 코멘트 입력 형식은 설계에서 구체화한다. 실제 사용자 계정이나 알림 서비스는 요구하지 않는다.

### FR-08. 외부 구현 상태의 수동 관리

근거: Q8 A 및 상세 설명, Q5 상세 설명.

계획이 끝난 SR을 구현 대기로 표시하고, 개발자가 외부에서 구현한 뒤 수동으로 구현 완료 처리한다.

수용 기준: 구현 대기 SR을 사용자가 구현 완료로 전환할 수 있다. 코드 실행·커밋·PR 연동 없이도 이 상태 전환이 가능하다. 완료 표시는 사용자의 선언이며 자동으로 검증된 빌드 성공을 뜻하지 않는다.

### FR-09. 향후 Jira 연동을 위한 골격

근거: Q2 상세 설명.

SR 직접 생성 흐름과 외부 입력 연결 지점을 분리하여, 이후 Jira 입력을 추가할 수 있는 인터페이스 골격을 둔다. 첫 버전에 Jira 네트워크 호출·인증·동기화는 구현하지 않는다.

수용 기준: 직접 생성 흐름이 Jira 설정 없이 동작하며, 코드 검토에서 외부 SR 입력을 연결할 경계를 확인할 수 있다. UI에 실제로 사용할 수 없는 Jira 기능을 사용 가능한 기능처럼 표시하지 않는다.

## 6. MVP 인수 시나리오

아래는 구현 후 검증할 기준이며 현재 실행 결과가 아니다.

1. 로컬 앱을 열어 제목·설명과 선택적 마크다운으로 SR을 직접 생성한다.
2. 다음 단계 진행으로 실제 Claude Code CLI를 실행하고 생성 중 표시 및 저장된 요구사항·계획 문서를 확인한다.
3. 필요한 질문에 응답하고 문서에 대한 결정 또는 수정 요청을 남긴 뒤 다음 계획 단계로 진행한다.
4. Inception 또는 Construction 반복 진행 시 회차 표시를 확인한다.
5. 문서를 수정하고 AI 생성·사람의 수정·결정 이력을 조회한다. 두 버전을 비교하고 이전 내용을 복원한 뒤 과거 이력이 유지되는지 확인한다.
6. 계획 단계에서 리뷰를 요청하고 카드가 기존 열에 남는지 확인한다. 리뷰가 진행 중이어도 후속 계획을 진행하고, 역할을 전환해 대상 버전에 대한 검토 결과를 기록한다.
7. 계획을 마쳐 구현 대기로 이동하고, 외부 구현을 마쳤다는 사용자 조작으로 구현 완료 표시를 확인한다.
8. 저장한 SR과 문서·이력을 다시 열어 확인하고, 핵심 입력 및 진행 조작을 키보드로 수행한다.

별도 실패 경로 확인: CLI 실행 실패 시 실패 상태가 표시되고 문서 생성이나 단계 완료로 오인되지 않는지 확인한다. 실제 실행 명령·테스트 방법은 Construction에서 정한다.

활성화된 확장 규칙이 없으므로 확장에 의한 차단 항목은 없다. 이는 운영 보안이나 복원력 검증을 완료했다는 의미가 아니다.

## 8. 이후 설계 항목과 승인

언어·프레임워크·저장 방식, CLI 실행 방식과 문서 결과 수집, SR별 실행 문맥 구분, 회차 계산, 문서·결정·리뷰의 연결 모델, 단계 전환 조건은 이후 설계에서 구체화한다. 제품 범위의 미응답 질문은 없으며, 이 항목들은 현재 요구사항을 구현하기 위한 설계 결정이다.

User Stories는 신규 사용자 기능, 계획 작성·검토 흐름, 작성자·리뷰어 역할 및 복원 시나리오를 수용 기준으로 구체화하는 데 필요하므로 실행 대상으로 판단한다. 요구사항 승인 후 해당 단계의 계획부터 진행한다.

[요구사항 검토 응답](requirements-approval-questions.md)의 A로 승인되었다. User Stories 계획으로 진행한다.
