# PlanRepo 제품 요구사항

버전은 0.4입니다. 상태는 **사용자 승인 완료**입니다. 질문 답변과 대화의 결정을 통합하고, 필요한 조건과 검토 사례를 이 프로젝트에 정리했습니다. 승인 응답은 “오케이진행해”이며 기록 시각은 2026-09-08T11:38:21Z입니다.

## 1. 요청과 분석 범위

사용자는 PlanRepo 서비스를 구축하고 AI-DLC 워크플로우를 시작하도록 요청했습니다. 요구사항과 검토 사례는 현재 프로젝트의 자산으로 통합했습니다.

- 요청 유형은 신규 프로젝트입니다. 작업 폴더는 Greenfield입니다.
- 범위는 팀의 SR별 질문·요구사항·계획·결정·동료 검토·승인·구현 인계를 관리하는 서비스 전체입니다.
- 복잡도는 Complex이며 Requirements Analysis의 깊이는 Comprehensive입니다.
- 첫 결과물은 가상 사용자와 가상 데이터로 검증하는 기능 데모입니다.
- 개발 도구는 Codex입니다. 제품의 첫 AI 실행 연결은 시스템에 설치된 Claude CLI입니다.
- 제품명 PlanRepo는 원본 입력서의 AI DLC Workbench와 같은 제품을 가리킵니다.

핵심 목표는 구현 전에 관계자가 요구사항과 계획을 이해하고 검토한 기준본을 확정하는 것입니다. 구현 준비 완료는 현재 범위의 질문·결정·수정 요청과 필수 승인을 처리해 유효한 구현 기준본을 만들 수 있다는 뜻입니다. 실제 코드 정확성이나 배포 성공을 뜻하지 않습니다.

## 2. 문서 기준과 프로젝트 경로

이 문서는 PlanRepo의 현재 제품 요구사항을 자체 완결 형태로 정의합니다. FR·NFR·AC, 게이트 정책, 화면·데이터·검토 흐름의 필수 조건은 본문에 포함했습니다. 다른 문서의 생략된 조건을 자동으로 상속하지 않습니다.

모든 파일 경로는 프로젝트 루트 기준입니다. 제품 검토는 `aidlc-docs/inception/requirements/requirements.md`에서 시작합니다. 상태는 `aidlc-docs/aidlc-state.md`, 프로젝트 재개 안내는 `aidlc-docs/README.md`에 있습니다.

질문·답변 기록은 `aidlc-docs/inception/requirements/requirement-verification-questions.md`에 있습니다. 자체 완결 검토 사례는 `aidlc-docs/inception/requirements/reference-context.md`에 있습니다. 두 파일은 근거와 검토 보조 자료이며 이 문서의 필수 조건을 대신하지 않습니다.

기준 워크플로우는 프로젝트에 포함된 `.aidlc-rule-details/`의 AI-DLC v1.0.1 규칙입니다. 원본의 단계와 PlanRepo의 보드 단계·검토 게이트를 구분합니다. G1·G2, 검토자 배정, 승인 버전과 변경 전파는 PlanRepo의 제품 정책입니다. SR의 workflowVersion은 v1.0.1로 고정합니다. 자동 업그레이드와 기존 SR 마이그레이션은 후속 범위입니다.

## 4. MVP 범위와 사용자

### 4.1 범위

SR 직접 등록과 가상 Jira 가져오기, 질문·후속 질문·결정, 문서 생성·편집·버전 비교, 섹션 댓글·수정 요청, 공식 검토·승인, 단계 전환 검사, 팀 보드·내 검토함, Handoff 내보내기와 활동 이력을 구현합니다.

저장, 버전, 권한, 승인, 차단과 재검토는 실제로 동작해야 합니다. 새로고침 후에도 상태를 유지합니다. Jira·GitHub Mock은 연결 상태를 명확히 표시합니다. 제품 AI의 완료 기준은 실제 Claude 실행이며 Mock만으로 충족하지 않습니다. 테스트용 대체 연결은 실제 실행과 구분합니다.

SR 하나는 하나의 구현 단위를 다룹니다. 여러 구현 단위의 자동 분해·병렬 실행·교차 의존성 관리는 제외합니다. 이 제한은 제품이 관리하는 SR의 범위이며 PlanRepo 개발 작업 자체를 한 파일이나 한 구성요소로 제한하지 않습니다.

### 4.2 역할과 공통 권한

| 역할 | 책임 |
|---|---|
| SR 담당자 | 범위·문서·질문 반영·검토 요청·단계 전환·인계를 관리합니다. |
| 업무 확인자·요청자 | 목적·업무 규칙·완료 기준에 답변합니다. 지정되면 요구사항을 승인합니다. |
| 동료 검토자 | 배정된 묶음을 검토하고 댓글·수정 요청·승인·반영 확인을 합니다. |
| 결정권자 | 배정된 결정의 선택·근거를 확정하거나 재결정합니다. |
| 팀 관리자 | 검토 정책과 SR별 검토자를 지정합니다. 승인 조건을 우회할 수 없습니다. |

한 사람이 여러 역할을 맡을 수 있습니다. G1과 G2 각각에 담당자와 다른 동료 검토자가 최소 한 명 있어야 합니다. 지정 검토자 전원의 현재 묶음 승인이 필요합니다. 검토자가 없으면 차단합니다. AI나 자동화 계정은 사람의 승인과 결정 확정을 대신할 수 없습니다.

SR 담당자가 질문·결정의 G1/G2 필수 시점과 후속 범위 분류를 작성하거나 변경합니다. 공식 결정은 지정 결정권자가 확정합니다. 분류·변경 이유를 검토 묶음에 포함합니다. 현재 구현 범위를 줄이면 요구사항과 완료 기준을 함께 변경하고 필요한 재승인을 받습니다.

## 5. 단계와 승인 규칙

### 5.1 진행 단계

| 단계 | 다음 단계의 조건 |
|---|---|
| SR 접수 | 목적·설명·담당자가 있어야 합니다. |
| 요구사항 구체화 | G1을 통과해야 합니다. |
| 계획·설계 | G2를 통과해야 합니다. |
| 구현 준비 완료 | 담당자가 유효한 Handoff를 선택하고 인계·구현 시작을 기록합니다. |
| 구현 중 | 담당자가 완료 요약과 PR 링크 또는 검증 결과 요약 등의 근거를 등록합니다. |
| 구현 완료 | 종결 상태를 유지하며 변경은 재검토 절차로 처리합니다. |

구현 중·완료는 외부 구현 사실의 수동 추적입니다. PlanRepo가 외부 테스트나 배포의 성공을 자동 검증했다고 표시하지 않습니다.

검토 요청의 상태는 작성 중, 검토 요청, 검토 중, 수정 필요, 승인 완료, 재검토 필요입니다. 보드의 진행 단계와 별도로 표시합니다. 일반 댓글과 비공식 의견은 G1·G2 공식 승인을 대신하지 않습니다.

### 5.2 G1 요구사항 승인

요구사항 문서가 있고 현재 요구사항 확정에 필수인 질문·결정이 처리되어야 합니다. 차단 수정 요청이 남아 있으면 안 됩니다. 현재 G1 ReviewBundle을 지정 검토자 전원이 승인해야 합니다.

검토 체크리스트에는 문제·대상 사용자, 포함·제외 범위, 업무 규칙·상태·경계, 검증 가능한 완료 기준, 예외·실패 기대 결과, 시스템·데이터·제약·영향, 확인 근거와 미확인 사항을 포함합니다. 문서 존재나 AI 점수만으로 내용의 완전성을 인증하지 않습니다.

### 5.3 G2 구현 준비 승인

G2 묶음은 입력으로 사용한 승인 G1 묶음의 ID·버전을 고정합니다. 유효한 G1을 참조해야 합니다. 진행 계획, 선택한 단계의 설계, 구체적 구현 계획이 있어야 합니다. 현재 구현 범위의 질문·결정·차단 수정 요청을 처리하고 현재 G2 ReviewBundle을 지정 검토자 전원이 승인해야 합니다.

실행·생략 단계와 이유, 변경 영향, 요구사항 ID와 구현 작업의 연결, 구현 순서, 검증 방법·회귀 항목, 기존 시스템의 적용·복구 고려사항을 검토합니다. 검증 방법은 구현 계획에 포함할 수 있으며 별도 테스트 전략 문서를 항상 강제하지 않습니다.

G1·G2 자체와 필수 문서는 생략할 수 없습니다. G2에서 정할 항목은 G1을 차단하지 않습니다. 후속 범위는 이번 구현 대상에서 제외한 항목이며 G2에서 결정할 필수 항목과 구분합니다. 후속 범위로 연기한 항목은 이유·담당자·재검토 시점을 기록합니다. 현재 구현에 필요한 결정을 단순히 연기해 차단을 해제하지 않습니다.

### 5.4 버전과 변경 전파

| 변경 | 처리 |
|---|---|
| G1의 요구사항·질문 처리 결과·업무 결정·근거 변경 | G1과 종속 G2를 재검토하고 신규 인계를 차단합니다. |
| G2의 계획·설계·구현 계획·관련 결정 변경 | G1을 유지하고 G2를 재검토합니다. |
| 새 차단 질문·수정 요청 | 영향받는 게이트를 즉시 차단합니다. G1이 무효이면 종속 G2와 신규 인계도 차단합니다. |
| 필수 검토자 변경·기존 SR에 정책 명시 적용 | 새 묶음으로 재승인합니다. G1이 바뀌면 G2도 재검토합니다. |
| 일반 댓글·조회·근거가 같은 링크 표시명 변경 | 승인 대상 내용·조건이 같으면 승인을 유지합니다. |
| 구현 시작 후 승인 내용 변경 | 검토 단계로 복귀하고 과거 Handoff와 외부 구현 상태를 함께 보존합니다. |

복귀는 영향받는 게이트를 이미 통과한 경우에만 적용합니다. 아직 통과하지 않았으면 현재 단계에서 검토를 갱신합니다. G2 전용 문서가 생겼다는 이유만으로 G1을 무효화하지 않습니다.

ReviewBundle은 문서·결정·질문 결과·검토자·정책의 버전을 고정합니다. 승인·댓글·수정 요청의 진행 이력은 별도로 보존합니다. 미해결 차단 요청은 새 문서 버전에 연결하여 이어갑니다. 이전 묶음의 미처리 검토 요청은 이전 버전 이력으로 보존하고 현재 검토함에 중복 표시하지 않습니다. 새 묶음 생성만으로 기존 차단 요청을 해결 처리하지 않습니다. G1 재승인 후 G2 문서와의 일관성을 확인하고 새 G2 묶음을 승인합니다. G2의 과거 승인을 자동 복구하지 않습니다. 재검토 여부는 검토 대상 내용의 변경으로 판단합니다. AI가 의미 변화가 작다고 판단해 재검토를 생략하지 않습니다.

## 6. 기능 요구사항

다음 23개 항목과 관련 절의 조건을 제품의 기능 요구사항으로 적용합니다.

| ID | 요구사항 |
|---|---|
| FR-01 | SR 키·제목·목적·설명·담당자·프로젝트를 등록합니다. Jira 키·URL, 참조 자료와 기존 시스템 여부는 선택 입력입니다. Git 연결 없이 시작할 수 있습니다. |
| FR-02 | 텍스트·Markdown·링크로 근거를 연결하고 읽지 못한 자료는 미확인으로 표시합니다. 기존 시스템 근거가 부족하면 필수 확인 항목으로 남깁니다. |
| FR-03 | 최초 설명을 보존하고 변경을 합의에 자동 적용하지 않습니다. Jira 중복 키를 알리고 기존 SR을 덮어쓰지 않습니다. |
| FR-04 | AI 질문에 이유·출처·관련 문서·답변 담당자·필요 시점을 표시합니다. 근거 있는 답변 후보도 사람의 확인을 거칩니다. |
| FR-05 | 선택형·자유 입력을 지원하고 선택형에도 직접 작성 경로를 둡니다. 답변됨과 해결됨을 구분합니다. 담당자가 근거·일관성·문서 반영 또는 변경 불필요 이유를 확인해 해결하거나 후속 질문을 등록합니다. AI 판단만으로 필수 질문을 닫지 않습니다. |
| FR-06 | 질문과 결정을 구분합니다. 전환 시 연결을 보존하고 같은 문제를 중복 집계하지 않습니다. |
| FR-07 | 결정의 질문·대안·영향·선택·이유·근거·시각·결정권자를 기록합니다. 지정 결정권자만 확정·재결정합니다. |
| FR-08 | 요구사항·진행 계획·설계·구현 계획을 구분합니다. 요구사항 ID·완료 기준과 구현 작업을 연결합니다. |
| FR-09 | 입력 버전·작업 유형을 기록하고 대기·진행·성공·실패·취소 상태를 제공합니다. 생성 결과는 담당자가 적용하기 전까지 초안이며 재시도 이력을 보존합니다. |
| FR-10 | 생성 중 입력 변경이 있으면 오래된 결과로 표시하고 바로 적용하지 못하게 합니다. 재생성하거나 사람이 차이를 검토해 현재 초안으로 반영합니다. |
| FR-11 | Markdown 열람·편집·버전 비교를 제공합니다. 변경 요약에 바뀐 요구사항·결정·문서 섹션을 표시하고 원문 비교로 확인할 수 있어야 합니다. |
| FR-12 | 문서 버전·섹션에 댓글과 수정 요청을 연결하고 차단 여부·담당자를 지정합니다. 반영자는 열림 상태를 반영 확인 대기로 바꾸고 요청자 또는 지정 검토자가 해결을 확인합니다. 섹션 삭제 시 미해결 요청을 별도 목록에 보존합니다. |
| FR-13 | 공식 ReviewBundle에 문서·결정·필수 질문 결과·검토자·정책 버전을 고정합니다. |
| FR-14 | 현재 묶음과 필수 체크리스트를 확인한 뒤 승인·수정 요청합니다. ReviewBundle ID·버전, 확인한 체크리스트, 승인자·범위·결과·시각을 기록하고 이전 화면의 승인은 거부합니다. |
| FR-15 | 승인 내용·필수 조건 변경 시 재검토와 새 묶음을 요구합니다. 과거 승인을 보존하고 변경 이유와 재검토 범위를 표시합니다. |
| FR-16 | 전환 시 권한·현재 버전·산출물·질문·결정·수정 요청·승인을 함께 검사합니다. UI와 직접 요청에 같은 검사를 적용하고 실패 사유·담당자·대상 링크를 제공합니다. AI의 승인 문구와 클라이언트가 보낸 완료 값은 통과 근거로 사용하지 않습니다. |
| FR-17 | 보드에서 진행 단계·검토 상태·차단 사유·다음 행동·담당자를 표시합니다. SR 키·제목 검색과 담당자·검토 필요·차단 필터, 명시적 단계 전환 버튼을 제공합니다. |
| FR-18 | 개인의 질문·결정·검토·수정·반영 확인을 검토함에 모읍니다. 기한 초과·현재 단계 차단·직접 요청·최신순으로 정렬하고 중복 요청을 정리합니다. |
| FR-19 | G1·G2의 역할·체크리스트·검토자와 정책 버전을 관리합니다. 변경을 기존 SR에 자동 소급하지 않습니다. |
| FR-20 | 유효한 G2에서 정확한 문서·결정·승인 버전의 Handoff를 생성합니다. ID·시각·승인·검증 기준·후속 범위를 포함해 미리보기와 Markdown 내보내기를 제공합니다. |
| FR-21 | 외부 구현 시작·완료·링크·근거를 수동 기록합니다. 변경 제안과 새 인계 필요 상태를 표시하고 과거 인계·외부 구현 이력을 유지합니다. |
| FR-22 | 생성·적용·답변·결정·검토·승인·정책·전환·인계를 행위자·대상 버전·시각과 함께 기록합니다. 일반 UI에서 이력을 수정·삭제하지 않습니다. |
| FR-23 | AI 연결을 워크플로우·저장·승인 로직과 분리합니다. provider와 model을 설정으로 선택할 수 있게 하고 첫 실제 연결은 설치된 Claude CLI를 사용합니다. |

FR-23은 DEC-02에서 추가했습니다. 새 provider 연결을 구현할 때 공통 생성 계약을 통해 연결합니다. MVP에서 두 번째 실제 provider 구현이나 모델 선택 전용 화면까지 만들 필요는 없습니다. 교체 가능성은 테스트용 연결로 검증합니다.

## 7. 비기능 요구사항

- **NFR-01 — 저장과 복구.** 새로고침·재접속 후 SR·답변·문서 버전·승인·인계를 보존합니다. 저장 실패를 성공으로 표시하지 않습니다.
- **NFR-02 — 변경 충돌.** 같은 문서를 두 화면에서 편집·검토하면 버전 충돌을 감지합니다. 이전 저장·승인으로 최신 상태를 덮어쓰지 않습니다.
- **NFR-03 — 일관된 전환.** 전환·Handoff 직전에 현재 게이트를 다시 검사합니다. 동시 변경과 반복 요청이 무효한 성공이나 중복 이력을 만들지 않아야 합니다.
- **NFR-04 — 권한.** 화면과 상태 변경 요청에 같은 역할 검사를 적용합니다. 데모 사용자 전환을 실제 조직 인증으로 표시하지 않습니다.
- **NFR-05 — 표시 안전성과 접근성.** Markdown의 실행 가능한 HTML·스크립트를 실행하지 않습니다. 출처를 표시하고 주요 행동을 키보드로 처리할 수 있게 합니다. 색만으로 상태를 구분하지 않습니다.
- **NFR-06 — 반응과 작업 상태.** 저장·생성의 진행·성공·실패를 표시합니다. 긴 생성 중에도 기존 문서 열람·검토가 가능해야 합니다. 검증용 규모·응답시간·문서 크기 목표는 NFR 단계에서 정합니다.
- **NFR-07 — 자료와 외부 호출.** 가상 데이터만 사용합니다. 실제 사내 자료를 쓰는 후속 운영 환경은 허용 모델·통신 경로·보관 위치를 먼저 확정합니다.
- **NFR-08 — AI 실행 경계.** 제품의 Claude 실행은 질문·결정 제안·문서 초안 생성에 한정합니다. 임의 명령·파일 수정·승인·단계 전환을 모델에 맡기지 않습니다. 실행 실패·응답 형식 오류·취소를 기록하고 기존 문서·승인을 보존합니다.

NFR-08은 실제 로컬 CLI 연결에 따라 FR-09·10·16의 경계를 구체화한 요구사항입니다. 비밀 값은 화면·로그·인계본에 노출하지 않습니다. 다른 SR의 세션이나 작업 내용을 현재 입력에 섞지 않습니다.

## 8. AI 실행과 기록

각 GenerationRun은 작업 유형, SR, 입력 버전, provider, 요청 모델 설정, 확인 가능한 실제 실행 모델·CLI 버전, 상태·오류, 결과 초안과 적용 이력을 기록합니다. 확인하지 못한 실제 모델 정보는 추정하지 않습니다.

설치된 Claude가 SR 입력과 필요한 v1.0.1 규칙을 받아 지원하는 질문·결정 제안·산출물 형식으로 결과를 반환하게 합니다. 결과의 형식과 입력 버전을 검사한 뒤 초안으로 등록합니다. AI 응답 안의 승인 문구는 게이트 통과 근거가 될 수 없습니다.

비대화식 호출과 구조화된 출력, 실행별 문맥 분리, 도구 제한, 취소·시간 제한·출력 오류 처리의 구체적인 방법은 Application Design과 필요한 NFR 설계에서 정합니다. 기능 데모는 로컬 Claude를 실행할 수 있는 환경을 전제로 합니다.

전역 개발 도구 설정을 제품의 상태 저장소로 사용하지 않습니다. CLI가 없거나 사용할 수 없으면 연결 실패를 표시합니다. Mock 결과를 실제 Claude 결과로 바꿔 표시하지 않습니다.

## 9. 화면과 대표 흐름

한국어 UI를 기본으로 합니다. 상단에는 제품명·프로젝트·현재 사용자를 표시합니다. 기본 메뉴는 팀 보드, 내 검토함, SR 목록, 팀 설정입니다.

팀 보드에는 SR 키·제목·담당자·진행 단계·검토 상태·차단 사유·다음 행동을 표시합니다. 보조 정보는 최근 변경 시각과 연결된 외부 작업입니다. 단계 전환의 드래그 앤 드롭은 제외합니다. 전체 퍼센트 대신 필수 질문 수나 현재 승인 수처럼 의미가 분명한 수치를 사용합니다.

내 검토함은 전체, 질문·결정, 문서 검토, 수정·확인 탭을 제공합니다. 항목에 SR, 요청 내용, 대상 버전·섹션, 요청자·담당자, 기한과 차단 여부를 표시합니다. 항목에서 SR 상세의 실제 처리 대상을 엽니다. 목록 요약만 보고 공식 승인하지 않습니다.

SR 상세 헤더에 제목·현재 단계·다음 행동·담당자·검토자·최신 저장 상태를 표시합니다. 기본 탭은 검토 요약입니다. 검토 요약에는 이번 범위·지난 버전 대비 변경점·질문·결정·수정 요청·G1/G2 조건을 표시합니다. 나머지는 질문·결정, 요구사항, 진행 계획·설계, 구현 계획, 활동 이력입니다. 넓은 검토 영역과 접을 수 있는 단계·통과 조건 패널을 사용합니다. 문서의 현재 버전·승인 상태와 이전 버전 비교·섹션 댓글·공식 검토 요청을 제공합니다. 승인 버튼에도 검토 묶음 버전을 표시합니다. 생성 패널에서 초안 생성·보완 요청과 작업 상태·결과를 확인합니다. 원시 CLI 출력이나 터미널을 고정해 놓지 않습니다.

첫 SR이 없으면 등록 또는 데모 가져오기를 안내합니다. 미배정 담당자·검토자와 근거 부족은 다음 행동으로 표시합니다. 저장·생성 실패 시 입력 내용과 이전 승인본을 보존하고 재시도 방법을 제공합니다. 오래된 저장·승인 요청에는 최신 변경을 보여주고 덮어쓰기를 막습니다. 삭제된 섹션의 미해결 요청은 별도 목록에서 처리합니다.

상태는 텍스트·아이콘·숫자를 함께 사용합니다. 실제 AI 실행 여부, Mock 연결, 저장 실패와 권한 부족을 명확히 표시합니다. Git 저장소 선택을 서비스 시작 조건으로 요구하지 않습니다.

대표 흐름은 다음과 같습니다. SR 등록 후 질문과 결정을 반영해 G1을 승인합니다. 진행 계획·설계·구현 계획을 검토하고 G2와 Handoff를 만듭니다. 승인 뒤 변경하면 영향받는 게이트를 다시 검토하고 새 인계를 생성합니다.

## 10. 데이터와 인계

다음 논리 데이터에서 필수 정보를 보존합니다. 특정 DB·ORM·API는 설계 단계에서 정합니다.

| 개념 | 보존할 정보 |
|---|---|
| SR | ID·키·설명 원문, 담당자, 단계·재검토 상태·외부 구현 상태, workflowVersion입니다. |
| ContextSource | SR, 자료 종류·대상·버전, 확인 여부·확인자·시각입니다. |
| ArtifactVersion | 문서 ID·종류·내용·버전, 요구사항 ID·섹션 ID, 입력 버전·작성 주체입니다. |
| Question | 질문·이유·담당자·상태, 답변·근거, 필요한 게이트, 연결된 결정·문서입니다. |
| DecisionVersion | 질문·대안·영향, 결정권자·결과·이유·근거·시각·버전, 후속 범위 분류입니다. |
| ReviewBundle | 게이트·ID·버전, 문서·결정·질문 참조, 상위 G1 묶음, 필수 검토자·정책 버전·상태입니다. |
| ReviewRequest·Approval | 대상 묶음·사용자·요청 유형·기한, 결과·확인 체크리스트·행위자·시각입니다. |
| ChangeRequest·Comment | 문서 버전·섹션·내용·차단 여부·담당자, 요청자·반영자·확인자·상태입니다. |
| WorkflowPlan·ReviewPolicy | 선택 단계·생략 이유·체크리스트, 게이트·검토 역할·정책 버전입니다. |
| GenerationRun | SR·작업 유형·입력 버전·provider·모델·CLI 버전, 상태·오류·결과·적용 이력입니다. |
| Handoff·ActivityEvent | 인계 버전·승인 정보·외부 연결과 주요 행동의 행위자·대상·시각입니다. |

본문과 승인 상태를 한 필드로 덮어쓰지 않습니다. 최신 버전·유효 승인과 과거 이력을 구분합니다. Jira 상태와 PlanRepo 단계는 별도 값입니다.

Handoff는 사람이 외부 코드 에이전트에 전달하는 Markdown 기준본입니다. 문서·결정·질문 처리와 검증 기준, 승인 정보, 후속 범위, workflowVersion을 식별할 수 있어야 합니다. G1·G2가 무효이면 현재 구현을 위한 새 기준본을 만들거나 내보낼 수 없습니다.

단일 Markdown 내보내기만으로 외부 에이전트가 AI-DLC 상태를 자동 복원한다고 보장하지 않습니다. 원본 워크플로우를 재개하려면 현재 단계·unit·다음 작업, 관련 문서·코드, 구현 계획과 승인 상태를 읽어야 합니다. 이를 도구별로 자동 복원하는 기능은 이번 범위에 포함하지 않습니다.

제품이 외부 CLI·저장소·이미 다운로드한 인계본을 자동 통제한다고 표현하지 않습니다. 운영 인증·운영 배포·조직의 실제 자료 처리와 두 번째 실제 AI provider 연결은 별도 후속 범위입니다.

## 15. 확인된 환경과 남은 검증

실행 파일은 프로젝트 루트에서 `command -v claude`로 PATH를 통해 찾습니다. 개인 설치 경로를 고정하지 않습니다. 확인한 `claude --version` 결과는 2.1.263 (Claude Code)입니다. 설치 도움말에서 비대화식 실행, JSON·구조화 출력, model 지정과 도구 제한 옵션을 확인했습니다.

요구사항 승인 시점에는 설치와 옵션만 확인했고 실제 생성 호출·인증·특정 모델 ID는 미검증이었습니다. 2026-09-09 구현 결정에서는 기존 PATH·HOME·인증 환경을 유지한 실제 호출이 exit 0으로 끝났고 actual model `global.anthropic.claude-opus-4-8`, canonical model `claude-opus-4-8`, provider `bedrock`을 확인했습니다. 제품 출력 schema, AC-17 전체 흐름, timeout·취소·자손 정리와 전역 문맥 격리는 후속 구현 검증 대상입니다. 프로젝트 문서와 설정은 현재 프로젝트 루트를 기준으로 해석합니다. 시스템에 사용 가능한 Claude CLI가 설치되어 있어야 하며 다른 프로젝트 문서나 개인 시각화 폴더는 요구하지 않습니다.

이번 요구사항 단계에서 추가로 답해야 할 제품 범위 질문은 없습니다. 실제 생성과 장애 처리는 구현 검증에서 확인합니다. 구현 계획 승인이나 애플리케이션 테스트 통과는 아직 받거나 수행하지 않았습니다.
