# PlanRepo 검토 사례 맥락

이 문서는 이전 실습에서 얻은 검토 맥락을 독립적으로 읽을 수 있도록 정리한 참고 자료입니다. MRBS와 테이블오더의 기능을 PlanRepo의 개발 범위로 승인하지 않습니다. 사례 속 요청, 실습 가정, 제안, 미결정 사항과 승인 상태를 구분합니다.

## 1. 이전 실습의 목적과 적용 범위

이전 실습은 하나의 개발 건에 대한 요구사항과 plan을 관계자가 이해하고 질문하며 개정본을 검토·승인하는 제품을 구체화하려는 시도였습니다. 두 사례로 요구사항이 정해지고 plan이 발전하는 과정을 확인하려 했습니다. 실습 범위는 요구사항 탐색과 읽기 중심 시안 검토였으며, 사례 서비스의 구현·배포는 포함하지 않았습니다.

이전 실습의 범위 승인은 사례의 요구사항·plan 버전 승인과 구분합니다. 당시 Construction을 생략한 선택은 PlanRepo 개발 단계의 생략 근거가 아닙니다. 실습에서 확정된 제품 기술 스택이나 운영 조건은 없습니다.

## 2. MRBS: 회의실별 예약 승인 담당자 분리

참고 초안의 식별자는 DEMO-MRBS-001이며 버전은 0.1입니다. 초안은 미승인 상태입니다. 아래 내용은 그 실습을 재구성한 요약이며 현재 MRBS 기능이나 결함을 평가하지 않습니다.

### 출발 요청과 실습 가정

공개 요청의 요지는 회의실마다 담당자를 달리 두고 각 담당자가 자기 회의실의 예약만 승인하도록 하는 것입니다. 예약 승인 담당자에게 사용자·회의실 생성 등의 시스템 관리 권한까지 부여하고 싶지 않다는 요구도 포함합니다.

다음은 요청에 더한 미승인 실습 가정입니다.

- 기존 사내 로그인과 회의실 예약 신청 기능이 있습니다.
- A 회의실과 B 회의실에 서로 다른 담당자가 있습니다.
- 일반 직원은 예약을 신청하고 회의실 담당자는 예약 승인 여부를 판단합니다.
- 총무 책임자가 개발 plan의 최종 승인자 역할을 맡습니다. 예약 승인 담당자와 개발 plan 승인자는 별개입니다.

### 요구사항 초안 R-01부터 R-06

아래 ID는 MRBS 사례 안에서만 사용합니다. 요청에 근거한 항목도 사례의 승인된 요구사항 버전을 뜻하지 않습니다. 여섯 항목 모두 검토 중입니다.

| ID | 요구사항 초안 | 지위 |
|---|---|---|
| R-01 | 담당자는 배정된 회의실의 예약만 승인합니다. | 출발 요청에 근거합니다. |
| R-02 | 담당자 역할만으로 사용자·회의실 생성 등의 관리 권한을 얻지 않습니다. | 출발 요청에 근거합니다. |
| R-03 | 전체 관리자가 회의실과 담당자의 연결을 설정합니다. | 실습 제안입니다. |
| R-04 | 담당자는 자신이 처리할 승인 대기 예약을 찾습니다. | 업무 흐름을 위한 제안입니다. |
| R-05 | 승인 실행 시점에도 현재 담당 권한을 검사합니다. | R-01을 보장하기 위한 제안입니다. |
| R-06 | 승인 기록에 예약·처리자·처리 시각을 남깁니다. | 사후 확인을 위한 제안입니다. |

### 미결정 사항 D-01부터 D-05

다섯 항목 모두 답변과 확정이 없습니다. 아래 선택지는 합의된 정책이 아닙니다.

| ID | 결정할 내용 | 검토할 선택지와 영향 |
|---|---|---|
| D-01 | 담당자 부재 시 누가 대신 승인합니까? | 전체 관리자의 사유 기록 후 대행과 지정 대체 담당자 처리를 비교합니다. 미결정이면 예약이 계속 대기할 수 있습니다. |
| D-02 | 회의실 하나에 여러 담당자를 둡니까? | 주 담당자 한 명으로 시작하는 제안이 있습니다. 선택에 따라 배정 화면과 승인 규칙이 달라집니다. |
| D-03 | 담당자 변경 후 기존 대기 예약은 누가 처리합니까? | 처리 시점의 현재 담당자가 맡는 제안이 있습니다. 이전 담당자의 권한과 새 담당자의 할 일을 함께 확인해야 합니다. |
| D-04 | 반려·예약 변경·취소도 이번 범위에 포함합니까? | 포함할 동작을 명시해야 합니다. 승인 기능 변경만으로 나머지 동작의 범위를 확정하지 않습니다. |
| D-05 | 다른 회의실의 예약 내용을 조회할 수 있습니까? | 기존 조회 정책 유지 여부를 결정해야 합니다. 승인 제한이 조회 제한까지 뜻하지는 않습니다. |

### 검토 장면과 확인 기준

1. 일반 직원이 A 회의실 예약을 신청합니다. 기존 기능이라는 가정을 표시합니다.
2. A 담당자는 자신의 승인 대기 예약을 찾고 승인합니다. 검토자는 R-01·R-04·R-05·R-06이 목록, 권한 검사와 기록에 어떻게 연결되는지 확인합니다.
3. B 담당자가 같은 예약의 승인 요청을 직접 보내거나 담당자가 사용자 생성 기능을 실행하는 장면을 검토합니다. 각각 R-01·R-05와 R-02의 제한을 확인할 인수 기준 초안입니다.
4. 담당자가 바뀐 뒤 이전 화면에서 승인을 누르는 장면으로 D-03을 드러냅니다. 부재 상황으로 D-01을 드러냅니다. 구체적인 기대 결과는 두 결정의 답변 후 확정합니다.
5. 결정 후 요구사항, 인수 기준과 plan의 변경 이유를 함께 검토합니다. 승인자·승인 버전·시각을 남기고 이후 수정본의 승인은 별도로 기록합니다.

이 장면은 실행한 테스트 결과가 아닙니다. 코드 조사, 구현 방식, 일정·비용 추정과 승인된 plan도 없습니다. 사례의 개발 착수 판단에는 미결정 정책과 그에 따른 인수 기준·구현 영향의 검토가 남아 있습니다.

## 3. 테이블오더: 한 문장에서 요구사항을 구체화하기

유일하게 확정된 시작 요구는 다음 문장입니다.

> 음식점에서 고객이 테이블의 태블릿으로 메뉴를 보고 주문하면, 관리자가 실시간으로 주문을 확인하고 처리하는 시스템입니다.

주요 기능의 세부 범위, JWT, SSE, 자동 로그인, 장바구니, 관리 기능과 결제의 포함·제외는 미정입니다. 실시간 주문 확인이라는 요구만으로 SSE를 기술 선택으로 확정하지 않습니다. 이전에 제시된 상세 기능과 구현 예외 목록도 비교 참고자료이며 승인된 요구사항이 아닙니다.

검토 화면은 시작 문장, 질문 이유, 답변 담당자, 제안과 미결정 상태를 구분해야 합니다. 관계자의 답변과 결정으로 요구사항을 구체화한 뒤 plan 개정 이유와 검토 결과를 연결합니다. 답이 없는 질문을 화면 시안이나 AI 제안만으로 해결 처리하지 않습니다.

## 4. 사례와 결정의 격리

MRBS와 테이블오더는 요구사항·질문·결정·plan 버전·검토 결과를 각각 보존합니다. MRBS의 담당자 정책을 테이블오더에 적용하거나 한 사례의 승인을 다른 사례의 승인으로 사용하지 않습니다. MRBS 사례의 R·D·인수 기준 ID와 PlanRepo 제품의 FR·AC도 서로 다른 범위의 식별자입니다.

PlanRepo의 기본 가상 시드는 PAY-102 결제 취소, AUTH-331 로그인 오류 처리, NOTI-028 알림 수신 설정, CAT-093 상품 검색 필터입니다. MRBS와 테이블오더는 검토 흐름의 참고 사례이며 추가 시드 구현 의무를 만들지 않습니다. 사례의 기능·기술 선택과 이전 실습 도구를 PlanRepo 요구사항으로 옮기지 않습니다.

## 5. PlanRepo에서 확인할 검토 가치

다음 FR·AC는 PlanRepo 제품 요구사항의 ID입니다. 제품 요구사항은 `aidlc-docs/inception/requirements/requirements.md`에서 관리합니다.

| 검토 가치 | 사례에서 확인할 내용 | 연결 |
|---|---|---|
| 요청·가정·제안을 구분합니다. | MRBS의 R-01·R-02와 R-03부터 R-06의 근거 차이, 테이블오더의 확정 한 문장을 구분합니다. | FR-02·04·07·09, AC-01·03·08 |
| 필요한 질문을 드러냅니다. | D-01·D-03처럼 출발 요청에 없는 정책을 발견하고 답변·결정·반영 여부를 추적합니다. | FR-04·05·06·07, AC-02·03·15 |
| 자신의 다음 행동을 찾습니다. | 담당자가 처리할 대기 항목과 질문·결정·검토의 책임자를 찾습니다. | FR-17·18, AC-10·14 |
| 원문과 변경 이유를 이해합니다. | 결정 전후의 요구사항·인수 기준·plan 변경을 함께 비교합니다. | FR-08·11·13·14, AC-06·07·11 |
| 현재 권한과 승인 버전을 확인합니다. | 이전 화면·이전 담당자의 승인을 그대로 받아들이지 않고 수정본의 재승인을 구분합니다. | FR-14·15·16·19·20, AC-04·06·07·09·11 |
| 사례별 맥락을 보존합니다. | 다른 SR의 결정·승인·생성 입력을 섞지 않습니다. | FR-01·05·07·13·20, FR-23, NFR-08, AC-19 |

실제 검토에서는 관계자가 변경점·관련 원문·결정 이유·대상 버전을 찾고, 무엇을 승인하는지 설명할 수 있는지 관찰합니다. 보드에서 차단 사유와 담당자를 10초 안에 찾는 사용성 목표도 함께 확인합니다. 이 문서 자체는 사용성 목표나 구현 검증의 통과 증거가 아닙니다.
