# PlanRepo 개발 단위 분해 계획

버전은 0.1이며 **사용자 승인 완료**입니다. 사용자 응답 “진행해”를 2026-09-08T14:05:28Z에 기록해 분해 계획 0.1을 승인 처리했습니다. 승인된 절차에 따라 Units Generation Part 2의 산출물을 생성합니다.

## 1. 목표와 입력

PlanRepo 전체를 개발 단위 UOW-01 하나로 다루고 내부 모듈·구현 순서·검증 책임을 구분하는 안을 제시합니다. 기준은 다음 프로젝트 내부 문서입니다.

- 제품 범위와 조건은 `aidlc-docs/inception/requirements/requirements.md` 0.4입니다.
- 사용자 행동과 수용 기준은 `aidlc-docs/inception/user-stories/stories.md` 및 `aidlc-docs/inception/user-stories/personas.md` 0.1입니다.
- 실행 단계는 `aidlc-docs/inception/plans/execution-plan.md` 0.1입니다.
- 승인된 구조와 계약은 `aidlc-docs/inception/application-design/application-design.md` 및 그 문서가 연결한 상세 설계 4개입니다.
- 단계 규칙은 `.aidlc-rule-details/inception/units-generation.md`, 코드 조직 기준은 `.aidlc-rule-details/construction/code-generation.md`입니다.

모든 경로는 프로젝트 루트 기준입니다. 애플리케이션 코드·빌드 설정·서버 실행 명령은 아직 없습니다. 이번 계획의 검증은 문서의 완전성과 연결을 확인하는 것이며 실제 Claude 생성·앱 실행 결과가 아닙니다.

## 2. 질문 영역 평가

질문 영역 여섯 가지를 모두 검토했습니다. 이미 승인된 내용으로 아래 안을 제시할 수 있으므로 추가 업무 질문과 빈 답변 항목을 만들지 않습니다. 새로운 사용자 답변을 임의로 작성하지 않습니다. 이 문서의 실제 분해안은 계획 승인에서 검토받았습니다. 추가 질문이 생기면 사용자의 선호대로 현재 대화에서 받고 원문을 감사 기록에 남깁니다.

| 영역 | 확인한 근거 | 계획에서의 처리 |
|---|---|---|
| 스토리 묶음 | 요구사항 0.4와 스토리 0.1의 전체 범위가 승인됐습니다. 단계·화면별 구현 순서는 나누되 최종 UOW는 전체 흐름을 책임집니다. | 기존 승인으로 판단합니다. 스토리를 범위에서 빼거나 새 업무를 추가하지 않습니다. |

| 팀과 책임 | 한 팀·프로젝트·가상 사용자 데모와 Codex를 통한 개발이 정해졌습니다. 실제 조직별 독립 배포·소유 조직 요구가 없습니다. | 가상 제품 역할을 개발 팀으로 해석하지 않습니다. 실제 조직 담당자나 병렬 개발 팀을 임의로 배정하지 않습니다. |

## 3. 단위 경계와 대안

현재 단계 규칙은 monolith를 하나의 unit과 내부 논리 모듈로 정의합니다. 승인된 AD-01의 모듈형 단일 로컬 앱과 같은 방향입니다. code-generation 규칙의 여러 구조 예시는 코드 배치 패턴이며 현재 구조를 여러 단위로 나누어야 한다는 요구로 해석하지 않습니다.

| 안 | 판단 |
|---|---|
| 전체 앱을 UOW-01로 두고 내부 모듈과 구현 묶음을 나눕니다. | 추천합니다. 공유 저장·게이트·무효화·인계의 책임을 한 단위에서 검증하며 루트 실행과 단계별 승인을 유지합니다. |
| UI·게이트·AI·저장을 각각 별도 UOW로 나눕니다. | 채택하지 않습니다. 독립 배포 요구가 없고 승인된 공유 저장 경계와 사용자 흐름이 여러 단위의 완료에 걸립니다. 내부 책임 분리는 이미 C-01부터 C-09까지로 정의돼 있습니다. |

| 단위 | 이름·문서 식별자 | 책임·포함 범위 |
|---|---|---|
| UOW-01 | PlanRepo Local Application / planrepo | 승인된 34개 스토리, FR 23개·NFR 8개·AC 19개, C-01부터 C-09까지와 S-01부터 S-09까지의 계약 50개를 구현·검증합니다. |

UOW는 개발 계획 단위입니다. C 식별자는 논리 모듈이고 S 식별자는 앱 내부의 서비스 계약입니다. S 서비스를 독립 배포 서비스로 바꾸지 않습니다. 브라우저·백엔드·저장·Claude 자식 프로세스의 수를 UOW 수로 세지 않습니다. 제품의 “한 SR의 구현 단위 하나” 정책도 PlanRepo 개발 단위 개수와 별개로 유지합니다.

다른 제품 UOW에 대한 의존은 없습니다. 단위 의존 행렬은 UOW-01 하나이며 자기 의존은 N/A입니다. 내부 의존은 승인된 `aidlc-docs/inception/application-design/component-dependency.md`의 행렬과 11개 연결을 그대로 사용합니다. UI는 ApplicationServices를 호출하고, GenerationRuntime은 내부 작업 계약으로 취소·완료 상태를 교환합니다. provider에 업무 저장·승인 권한을 주지 않습니다.

설치된 Claude·PATH·사용 가능한 실행 환경은 명시적 시스템 전제입니다. 이 전제를 다른 개발 UOW나 이미 검증된 실제 생성으로 표시하지 않습니다. Jira·GitHub는 프로젝트의 가상 자산을 사용합니다. 외부 프로젝트 파일이나 전역 개발 도구 설정을 제품의 필수 문서·저장소로 삼지 않습니다.

## 4. Greenfield 코드 조직안

단일 단위 패턴에 따라 애플리케이션 코드는 프로젝트 루트의 `src/`, 테스트는 `tests/`, 제품 설정은 `config/`에 배치할 것을 제안합니다. 다음은 생성 예정인 논리 경로이며 현재 폴더가 있다는 뜻이 아닙니다.

| 구성요소 | 이름 | 예정 코드 경로 | 책임 |
|---|---|---|---|
| C-01 | WebUI | `src/web/` | 역할 선택·보드·검토함·상세·문서·생성·인계 화면을 둡니다. |
| C-02 | ApplicationServices | `src/application/` | S-01부터 S-09까지의 내부 서비스 계약과 트랜잭션 조정을 둡니다. |
| C-03 | DomainPolicies | `src/domain/` | 현재 역할·게이트·ReviewImpact의 순수 정책을 둡니다. |
| C-04 | LocalPersistence | `src/persistence/` | 영속 저장·불변 버전·현재 참조·일관된 조회를 둡니다. |
| C-05 | GenerationRuntime | `src/generation-runtime/` | 작업 인수·실행·취소 전달·종료 관찰을 둡니다. |
| C-06 | GenerationProviders | `src/providers/generation/` | Claude와 테스트 adapter·공통 provider 계약을 둡니다. |
| C-07 | ReferenceProviders | `src/providers/reference/` | Jira·GitHub Mock 조회와 명시적 링크 처리를 둡니다. |
| C-08 | DocumentPresentation | `src/presentation/` | 안전한 문서 표현·원문 비교·고정 인계 직렬화를 둡니다. |
| C-09 | ProjectRuntime | `src/runtime/` | 프로젝트 루트·PATH·설정·가상 사용자·제한 프로세스 실행을 둡니다. |

`tests/unit/`은 순수 정책·표현·작은 계약을, `tests/contract/`는 provider·저장·Mock 경계를, `tests/integration/`은 실제 저장과 업무 서비스의 경쟁·무효화를, `tests/e2e/`는 화면과 전체 사용자 흐름을 검증하는 논리 배치안입니다. 가상 사용자·시드·테스트 자료는 프로젝트 내부의 `config/`와 `tests/fixtures/`에서 역할을 나누며 실제 비밀 값은 포함하지 않습니다.

구체적인 언어·프레임워크·DB·파일 확장자·패키지 경계는 NFR Requirements에서 확정합니다. 공통 자료형과 composition root를 배치할 때 승인된 호출 방향을 유지하고 순환 참조를 만들지 않습니다. 브라우저에 backend 실행 코드나 비밀 설정을 노출하지 않습니다. 문서·검증 결과는 `aidlc-docs/`에 두며 앱 코드를 이 폴더에 만들지 않습니다.

## 5. 단위 내부 구현·검증 순서

아래 B 식별자는 UOW-01의 Code Generation 내부 묶음입니다. 별도 UOW·배포 서비스·Construction 단계가 아닙니다. 이 순서는 후속 상세 설계와 승인된 Code Generation 계획에서 파일·테스트 명령으로 구체화합니다. 지금 구현을 시작하는 체크리스트로 사용하지 않습니다.

| 묶음 | 목적 | 선행 묶음 |
|---|---|---|
| B-01 | 실행·저장과 SR 기반 | 없습니다. |
| B-02 | 초기 실제 AI와 편집 경로 | B-01 |
| B-03 | 질문·G1 검토와 정책 | B-02 |
| B-04 | 계획·G2와 구현 준비 | B-03 |
| B-05 | 인계·외부 구현 사실과 이력 | B-04 |
| B-06 | 승인 후 변경과 전체 화면 통합 | B-05 |

### B-01 실행·저장과 SR 기반

프로젝트 루트 실행, 가상 사용자·시드, SR·근거·초기 화면을 연결합니다. C-03 정책과 C-04 저장 경계에서 현재 역할·버전·중복·게이트 판정과 변경의 원자성을 먼저 검증합니다. 본격적인 G1/G2 사용자 흐름은 뒤 묶음에서 연결합니다.

### B-02 초기 실제 AI와 편집 경로

영속 생성 작업·실행 소유권·ProviderSelection 고정·취소 전달·실제 종료 관찰·출력 검사를 구현합니다. 설치된 Claude로 질문·문서·답변 반영 후속 생성을 실제 확인합니다. 질문·답변·결정·문서 편집과 사람의 초안 적용 기본 경로를 함께 준비합니다. 테스트 adapter로 실패·오래된 결과·취소·교체 계약을 재현합니다. 생성 중 검토와 승인 무효화가 남아 있으므로 US-009부터 US-013까지의 전체 완료로 집계하지 않습니다.

### B-03 질문·G1 검토와 정책

B-02의 답변·편집·적용 경로에 질문 해결·결정 전환·공식 묶음·수정 확인·개별 승인·G1 전환을 연결합니다. 정책 버전과 최초 검토자 배정을 구현합니다. 지정 전원·담당자 외 동료·현재 역할·이전 묶음 거절·중복 요청을 검증합니다. 변경 경로에는 ReviewImpact를 즉시 적용합니다.

### B-04 계획·G2와 구현 준비

WorkflowPlan·설계·구현 계획·검증 연결과 정확한 승인 G1 참조를 사용하는 G2 검토·전환을 연결합니다. 필수 문서·질문·결정·미해결 차단 수정 요청(반영 확인 대기 포함)을 우회하지 못하게 검증합니다.

### B-05 인계·외부 구현 사실과 이력

고정 Handoff·미리보기·Markdown 내보내기·수동 외부 시작/완료·과거 이력을 연결합니다. 무효한 현재 게이트와 반복 내보내기를 저장 확정 시점에 검사합니다. 실제 Claude의 결과에서 사람 적용·G1·G2·인계까지 AC-17 통합 흐름을 확인합니다.

### B-06 승인 후 변경과 전체 화면 통합

재결정·후속 범위·AI 적용·수동 편집·검토자/정책 변경과 G1/G2 재검토를 통합 검증합니다. 과거 인계·외부 진행 사실을 보존하고 오래된 G2를 자동 복구하지 않게 확인합니다. 보드·검토함·상세의 같은 상태, 생성 중 열람·검토, 권한·재접속·변경 경쟁·키보드·표시 안전성을 실제 화면에서 검증합니다.

각 묶음에서 해당 화면과 실제 서비스 경로를 함께 연결합니다. UI를 B-06에 처음 구현하지 않습니다. ReviewImpact·현재 권한·원자적 저장은 B-01에서 기반을 마련하고 이후 변경 경로마다 적용합니다. B-06은 이 규칙을 처음 추가하는 시점이 아니라 여러 기능이 함께 바뀌는 상황의 최종 확인 시점입니다.

초기 실제 Claude 실행이 막히면 판별 가능한 원인과 미검증 항목을 남깁니다. 독립적인 저장·게이트 구현은 계속할 수 있지만 실제 생성 기준을 Mock 성공으로 바꾸거나 AI 관련 스토리와 UOW를 완료 처리하지 않습니다. 도움말·버전 확인은 실제 질문·문서·후속 생성의 통과 증거가 아닙니다.

승인된 스토리 34개 각각을 정확히 한 묶음에 배정합니다. 개별 기준 122개와 각 스토리에 연결된 공통 기준 SC-01부터 SC-07까지를 유지합니다. 원본 스토리의 시작 조건과 의존 관계는 테스트할 상태를 설명하며 코드 구현 순서와 동일한 뜻이 아닙니다.

가상 승인 상태는 개별 검증의 시작 조건으로 준비할 수 있습니다. 실행 중인 쓰기 경로를 가짜 성공으로 대체한 결과를 실제 통합 통과로 집계하지 않습니다. 화면·서비스·저장을 연결한 해당 스토리의 전체 기준이 통과해야 완료입니다. 저장·권한·표시 안전성 같은 공통 조건은 해당 행동을 구현한 묶음에서 확인하고 최종 제품 검증에도 포함합니다.

NFR-01부터 NFR-08까지는 UOW-01 전체에 적용합니다. AC-17의 실제 Claude부터 사람의 검토·인계까지의 흐름은 B-05가 통합 검증을 책임집니다. provider 교체와 승인 이후 생성·변경의 상호작용은 B-06에서 마무리합니다. 최종 Build and Test는 모든 기준의 실행 증거와 빌드·전체 사용자 흐름을 확인하며 단위 내부 미완료 항목을 감추는 단계가 아닙니다.

원래 Workflow Planning의 실행 횟수 식은 3 + 5 × U였습니다. 이번 안의 U=1이면 그 시점 기준 8회입니다. 현재 남은 단계 수나 승인 횟수로 해석하지 않습니다. 실제 기간은 아직 측정 근거가 없어 숫자로 확정하지 않습니다.
