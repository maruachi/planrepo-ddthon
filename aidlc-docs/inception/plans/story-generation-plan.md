# PlanRepo 스토리 작성 계획

버전은 0.1입니다. 상태는 **작성 방식·산출물 승인 완료**입니다. 사용자 응답 “응진행해”를 2026-09-08T11:46:46Z에 기록했습니다. 사용자에게 승인받은 요구사항 0.4를 스토리로 정리하는 방법과 실행 순서를 제안합니다. 이 계획의 승인과 생성된 스토리의 승인은 별도입니다.

## 1. 입력과 산출물

모든 경로는 프로젝트 루트 기준입니다. 승인된 요구사항은 `aidlc-docs/inception/requirements/requirements.md`입니다. 내부 사례는 `aidlc-docs/inception/requirements/reference-context.md`입니다. 실행 필요성은 `aidlc-docs/inception/plans/user-stories-assessment.md`에 기록했습니다.

계획 승인 후 다음 필수 산출물을 생성합니다.

- `aidlc-docs/inception/user-stories/personas.md`에 역할별 사용자 원형과 스토리 연결을 정리합니다.
- `aidlc-docs/inception/user-stories/stories.md`에 사용자 스토리, 개별 수용 기준, 요구사항 추적과 품질 점검 결과를 정리합니다.

앱 코드, API 설계, 개발 일정과 sprint 계획은 이번 단계의 산출물이 아닙니다.

## 2. 작성 방식 비교와 제안

| 방식 | 장점 | 주의점 |
|---|---|---|
| 사용자 흐름 중심 | 접수부터 인계·변경까지 맥락과 통과 조건을 따라가기 쉽습니다. | 서로 다른 역할의 행동을 한 스토리에 과도하게 묶지 않아야 합니다. |
| 기능 중심 | 기능별 누락과 요구사항 대응을 찾기 쉽습니다. | 사용자 목적과 역할 간 인계가 약해질 수 있습니다. |
| 페르소나 중심 | 역할별 책임과 다음 행동이 명확합니다. | 같은 문서·검토 흐름이 여러 역할에 중복될 수 있습니다. |
| 도메인 중심 | SR·문서·검토·인계의 경계를 비교하기 쉽습니다. | 아직 확정하지 않은 구현 구조를 스토리에 고정할 수 있습니다. |
| Epic 중심 | 큰 범위를 여러 하위 스토리로 묶어 볼 수 있습니다. | 계층만 늘고 실제 사용자 행동이 모호해질 수 있습니다. |

**제안은 사용자 흐름 중심입니다.** 최상위 묶음은 아래의 여덟 흐름으로 정합니다. 그 안에서는 역할이 한 가지 목적을 달성하는 행동을 스토리 하나로 나눕니다. 기능 ID는 분류 기준을 대신하지 않고 누락 검증에 사용합니다.

흐름별로 역할과 목적을 분리하고, FR·NFR·AC로 요구사항 연결을 검증합니다.

## 3. 페르소나 구성

| ID | 역할 | 담을 목표와 경계 |
|---|---|---|
| P-01 | SR 담당자 | 요구를 정리하고 질문·문서 반영·검토 요청·인계를 관리합니다. 담당자 자신의 승인만으로 게이트를 통과하지 못합니다. |
| P-02 | 업무 확인자·요청자 | 목적·업무 규칙·완료 기준을 답합니다. 검토자로 지정된 경우에만 공식 승인 역할을 수행합니다. |
| P-03 | 동료 검토자 | 대상 버전·변경점·근거를 확인하고 수정 요청·승인·반영 확인을 합니다. |
| P-04 | 결정권자 | 배정된 대안의 영향·근거를 판단하고 확정·재결정합니다. 문서 승인과 결정 확정을 구분합니다. |
| P-05 | 팀 관리자 | 정책·필수 체크리스트·검토자를 관리합니다. 승인 우회 권한은 없습니다. |

각 페르소나에는 목표, 해야 하는 일, 겪는 어려움, 필요한 정보, 허용·제한 행동과 관련 스토리를 기록합니다. 실제 인명·나이·가상의 조직 배경은 추가하지 않습니다.

한 사람이 여러 역할을 맡는 경우는 허용합니다. 다만 각 필수 게이트에는 SR 담당자와 다른 동료 검토자가 최소 한 명 있어야 합니다. AI는 사람의 페르소나나 승인 주체로 만들지 않습니다. 모델 교체와 실행 제한은 관련 사용자 흐름의 지원 조건으로 다룹니다.

## 5. 스토리와 수용 기준 형식

각 스토리에 고유 ID, 제목, 주 페르소나, 사용자 목적, 관련 흐름, FR·NFR·제품 AC, 시작 조건과 의존 관계를 둡니다. 서술은 “이 역할의 사용자는 이 목적을 위해 이 행동을 할 수 있어야 합니다” 형식으로 씁니다.

각 수용 기준에는 **조건, 행동, 결과**를 구분합니다. 결과는 저장 상태·표시·거절 사유·버전·담당자·이력처럼 관찰 가능한 값으로 표현합니다. 사용자 목표 없는 구현 작업 목록이나 “정상 동작합니다” 같은 문구로 대신하지 않습니다.

스토리는 US-001부터 순차 식별합니다. 스토리별 수용 기준은 스토리 안의 C1·C2 순서로 식별하고 제품의 AC-01부터 AC-19와 구분합니다.

## 6. 반드시 연결할 검증 조건

| 범위 | 스토리에 포함할 핵심 조건 | 제품 수용 기준 |
|---|---|---|
| 입력과 질문·결정 | Git 없이 시작, 미확인 근거, 답변·해결 구분, 지정 결정권자, 전환 항목 중복 방지입니다. | AC-01, AC-02, AC-03 |
| 공식 검토·권한 | 검토자가 없거나 담당자 자신의 승인만 있으면 게이트 통과를 차단합니다. 미확인 수정 반영으로 차단을 해제하지 않습니다. 권한 없는 직접 요청과 이전 화면 승인을 거부합니다. | AC-04, AC-05, AC-09 |
| 변경 전파 | G1과 G2 전용 변경을 구분하고 새 차단 문제와 삭제된 섹션의 요청을 보존합니다. G1 재승인으로 과거 G2 승인을 복구하지 않습니다. | AC-06, AC-07, AC-15, AC-16 |
| 배정과 찾기 | 정책의 명시 적용, 현재 검토 요청의 중복 방지, 보드와 검토함의 일치, 실제 처리 대상 연결입니다. | AC-10, AC-14 |
| 저장·충돌 | 저장 실패 시 입력 보존, 오래된 버전 충돌, 반복 승인·전환·인계의 중복 방지입니다. | AC-09, AC-13 |
| AI 생성 | 실제 Claude의 질문·문서·후속 생성, 사람의 초안 적용, 오래된 결과, 교체 계약, 실패·취소·형식 오류·SR 문맥 분리입니다. | AC-08, AC-17, AC-18, AC-19 |
| 인계와 외부 구현 | 현재 승인 버전 일치, 무효 게이트의 신규 인계 차단, 과거 인계·외부 구현 이력 보존입니다. | AC-11, AC-12 |

NFR-01 저장·복구, NFR-02 충돌, NFR-03 원자적 전환·중복 방지는 상태를 바꾸는 스토리에 연결합니다. NFR-04 권한과 NFR-05 표시 안전성·키보드 접근성은 관련 행동·화면에 연결합니다. NFR-06 작업 상태와 NFR-07 가상 자료 사용은 생성·저장 흐름에 연결합니다. NFR-08 실행 경계는 AI 흐름에 연결합니다.

보드·검토함 관련 스토리에는 요구사항의 사용성 관찰도 연결합니다. 대표 사용자가 차단 이유와 담당자를 10초 안에 찾고, 실제 처리 대상에서 변경점·원문·결정 이유·대상 버전을 확인하는지 검증합니다. 문서 작성만으로 사용성 목표를 달성했다고 하지 않습니다.

모든 스토리에 모든 예외를 반복하지 않습니다. 행동과 직접 관련된 조건을 그 스토리에 두고 공유 조건은 명시적인 연결로 재사용합니다. 각 FR·NFR·제품 AC가 최소 한 스토리의 구체적인 조건에 연결되는지 추적표로 검증합니다.

## 7. INVEST 적용

- 독립성은 한 스토리의 결과를 준비된 시작 상태로 검증할 수 있는지를 확인합니다. 게이트 간 실제 업무 의존성은 숨기지 않고 기록합니다.
- 협의 가능성은 표현·분할·상세 구현에 적용합니다. 이미 승인한 업무 규칙을 변경하려면 요구사항 변경으로 처리합니다.
- 가치는 사용자가 얻는 결과로 설명합니다.
- 추정 가능성은 입력·권한·성공·거절 결과를 명확히 하는 것으로 확인합니다. 이번 단계에서 시간이나 sprint를 추정하지 않습니다.
- 크기는 한 역할의 목적 하나를 기준으로 점검합니다. 역할이나 별도 확정 행동이 달라지면 나눕니다.
- 검증 가능성은 각 수용 기준의 조건·행동·결과와 FR·NFR·AC 연결로 확인합니다.

## 9. 질문과 승인 상태

## 10. 범위와 확장 준수

필수 게이트, 지정 검토자 전원 승인, 담당자 외 동료, 단일 구현 단위, 실제 상태 검사와 모델의 승인 금지는 변경하지 않습니다. 참고 사례의 기능·기술 선택을 새 제품 기능으로 추가하지 않습니다.

Security Baseline, Resiliency Baseline, PBT는 No이며 개별 확장 규칙은 N/A입니다. 전체 규칙을 읽지 않습니다. 제품의 기존 NFR과 TDD는 유지합니다. 이 단계에서는 앱 코드와 실행 테스트를 생성하지 않습니다.
