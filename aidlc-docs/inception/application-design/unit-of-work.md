# PlanRepo 개발 단위 정의

버전은 0.1이며 **사용자 승인 완료**입니다. 승인된 `aidlc-docs/inception/plans/unit-of-work-plan.md` 0.1에 따라 생성했습니다. 사용자 응답 “응 진행해”를 2026-09-08T14:28:49Z에 기록해 단위 산출물 0.1을 승인 처리했습니다. 아래 완료 조건은 앞으로 구현·검증할 조건입니다.

## 1. 단위와 범위

| 항목 | 정의 |
|---|---|
| 개발 단위 | UOW-01입니다. |
| 이름 | PlanRepo Local Application입니다. |
| 문서·구현 식별자 | planrepo입니다. |
| 구조 | 브라우저 UI·로컬 백엔드·로컬 영속저장을 가진 모듈형 단일 앱입니다. |
| 개발 범위 | 승인된 스토리 34개·개별 수용 기준 122개·공통 기준 7개, FR 23개·NFR 8개·AC 19개 전체입니다. |
| 책임 | SR 등록부터 질문·결정·문서·G1·G2·재검토·Handoff·외부 구현 사실·활동 조회까지 연결합니다. |
| 현재 구현 상태 | 미착수입니다. 앱 코드·빌드·실제 생성·앱 테스트 결과는 아직 없습니다. |
| 다른 개발 단위 의존 | 없습니다. 내부 모듈 관계와 시스템 실행 전제는 별도로 관리합니다. |

업무 기준은 `aidlc-docs/inception/requirements/requirements.md` 0.4입니다. 구조·입출력 계약은 `aidlc-docs/inception/application-design/application-design.md` 0.1과 상세 설계를 따릅니다. 역할은 `aidlc-docs/inception/user-stories/personas.md`의 가상 사용자 다섯 역할을 사용합니다. UOW-01에 실제 조직별 개발 소유자를 임의 배정하지 않습니다.

C 식별자는 내부 모듈, S 식별자는 그 안의 서비스 계약, B 식별자는 Code Generation 내부 구현·검증 묶음입니다. 독립 배포 서비스나 별도 UOW가 아닙니다. Claude 자식 프로세스도 별도 UOW로 세지 않습니다. 제품의 “한 SR의 구현 단위 하나” 정책은 제품 기능으로 유지하며 이 개발 단위 경계의 근거로 혼동하지 않습니다.

## 2. 모듈 소유와 코드 조직

다음 경로는 프로젝트 루트에서 시작하는 구현 배치입니다. 현재 코드 폴더를 생성했다는 뜻이 아닙니다. UOW-01은 아래 모듈을 모두 소유합니다.

| 구성요소 | 이름 | 코드 경로 | 책임 |
|---|---|---|---|

`tests/unit/`은 순수 정책·표현 검증, `tests/contract/`는 provider·저장·Mock 계약 검증, `tests/integration/`은 실제 저장과 업무 서비스의 정합성 검증, `tests/e2e/`는 화면부터 저장까지의 사용자 흐름 검증에 사용합니다. `tests/fixtures/`와 `config/`에는 역할에 맞는 가상 자료·제품 설정을 둡니다. 실제 비밀 값은 시드·검증 로그·인계본에 넣지 않습니다.

문서는 `aidlc-docs/`에 둡니다. 앱 코드는 문서 폴더에 만들지 않습니다. 언어·프레임워크·DB·확장자·실행 명령은 후속 NFR·Infrastructure Design에서 구체화합니다. 공통 자료형과 composition root도 그때 배치하며 승인된 호출 방향을 유지합니다. 브라우저 코드에 백엔드 실행 기능이나 비밀 설정을 전달하지 않습니다.

## 3. 구현·검증 순서

모든 후속 설계와 Code Generation 계획의 승인을 받은 뒤 아래 순서로 구현합니다. 묶음의 완료와 스토리 전체 완료는 구분합니다. 최종 스토리 배정은 `aidlc-docs/inception/application-design/unit-of-work-story-map.md`, 선행 계약은 `aidlc-docs/inception/application-design/unit-of-work-dependency.md`에 있습니다.

| 묶음 | 구현·검증 내용 | 최종 담당 스토리 수 |
|---|---|---|
| B-01 | 실행·저장과 SR 기반 | 3개입니다. |
| B-02 | 초기 실제 AI와 편집 경로 | 0개입니다. |
| B-03 | 질문·G1 검토와 정책 | 10개입니다. |
| B-04 | 계획·G2와 구현 준비 | 4개입니다. |
| B-05 | 인계·외부 구현 사실과 이력 | 4개입니다. |
| B-06 | 승인 후 변경과 전체 화면 통합 | 13개입니다. |

### B-01 실행·저장과 SR 기반

프로젝트 루트 실행, 가상 사용자·시드, SR·근거·초기 화면을 연결합니다. C-03 정책과 C-04 저장 경계에서 현재 역할·버전·중복·게이트 판정과 변경의 원자성을 먼저 검증합니다. 본격적인 G1/G2 사용자 흐름은 뒤 묶음에서 연결합니다.

### B-02 초기 실제 AI와 편집 경로

영속 생성 작업·실행 소유권·ProviderSelection 고정·취소 전달·실제 종료 관찰·출력 검사를 구현합니다. 설치된 Claude로 질문·문서·답변 반영 후속 생성을 실제 확인합니다. 질문·답변·결정·문서 편집과 사람의 초안 적용 기본 경로를 함께 준비합니다. 테스트 adapter로 실패·오래된 결과·취소·교체 계약을 재현합니다. 생성 중 검토와 승인 무효화가 남아 있으므로 US-009부터 US-013까지의 전체 완료로 집계하지 않습니다.

### B-03 질문·G1 검토와 정책

B-02의 답변·편집·적용 경로에 질문 해결·결정 전환·공식 묶음·수정 확인·개별 승인·G1 전환을 연결합니다. 정책 버전과 최초 검토자 배정을 구현합니다. 지정 전원·담당자 외 동료·현재 역할·이전 묶음 거절·중복 요청을 검증합니다. 변경 경로에는 ReviewImpact를 즉시 적용합니다.

### B-04 계획·G2와 구현 준비

WorkflowPlan·설계·구현 계획·검증 연결과 정확한 승인 G1 참조를 사용하는 G2 검토·전환을 연결합니다. 필수 문서·질문·결정·미해결 차단 수정 요청(반영 확인 대기 포함)을 우회하지 못하게 검증합니다.

### B-05 인계·외부 구현 사실과 이력

고정 Handoff·미리보기·Markdown 내보내기·수동 외부 시작/완료·과거 이력을 연결합니다. 무효한 현재 게이트와 반복 내보내기를 저장 확정 시점에 검사합니다. 실제 Claude의 결과에서 사람 적용·G1·G2·인계까지 AC-17 통합 흐름을 확인합니다.

### B-06 승인 후 변경과 전체 화면 통합

재결정·후속 범위·AI 적용·수동 편집·검토자/정책 변경과 G1/G2 재검토를 통합 검증합니다. 과거 인계·외부 진행 사실을 보존하고 오래된 G2를 자동 복구하지 않게 확인합니다. 보드·검토함·상세의 같은 상태, 생성 중 열람·검토, 권한·재접속·변경 경쟁·키보드·표시 안전성을 실제 화면에서 검증합니다.

각 묶음에서 해당 UI와 실제 서비스 경로를 연결합니다. 현재 권한·ReviewImpact·원자적 저장을 B-01부터 준비하고 새 변경 경로에 계속 적용합니다. B-06은 이를 처음 구현하는 묶음이 아니라 여러 기능의 상호작용을 확인하는 묶음입니다.

B-02는 실제 Claude의 질문·문서·사람 답변을 반영한 후속 생성과 adapter 계약의 초기 실행 증거를 남깁니다. 생성 중 검토·승인 후 변경·교체 이후 동일한 승인 절차는 뒤 묶음에서 확인하므로 B-02만으로 AI 스토리를 완료 처리하지 않습니다. 실제 연결이 막히면 독립 작업은 진행할 수 있으나 실제 AI 수용 기준과 UOW는 미완료로 남깁니다.

## 4. 반드시 지킬 처리 경계

업무 변경·불변 버전·현재 참조·검토 무효화·요청 승계·활동·중복 요청 기록은 같은 저장 경계에서 확정합니다. 일반 댓글로 revision이 늘어난 사실만으로 승인 무효화를 결정하지 않습니다. 조회한 게이트 결과는 안내이며 실제 전환·현재용 인계 내보내기의 확정 시점에 현재 조건을 다시 검사합니다.

개별 승인과 게이트 통과를 분리합니다. 지정 전원·담당자 외 동료·필수 질문·결정과 미해결 차단 수정 요청을 검사합니다. 반영 확인 대기만으로 차단을 해제하지 않으며 비차단 요청을 임의로 차단으로 바꾸지 않습니다. 역할 겸임 자체를 거절 조건으로 추가하지 않습니다.

G1 기준 변경은 종속 G2·현재 인계에 영향을 주고 G2 전용 변경은 G1을 유지합니다. 새 검토자·정책 명시 적용·새 차단 문제는 새 묶음의 검토·승인을 필요로 합니다. 삭제된 섹션의 미해결 요청도 보존합니다. 재승인 과정에서 과거 G2를 자동 복원하지 않습니다.

긴 AI 호출은 업무 트랜잭션 밖에서 실행합니다. 요청의 입력 스냅샷과 provider/model 선택을 고정합니다. provider는 제안만 반환하고 사람의 적용·결정 확정·승인을 대신하지 않습니다. 취소된 실행의 늦은 결과는 terminal 상태를 바꾸지 못하며 실제 프로세스 종료 관찰은 별도 기록입니다.

Handoff는 정확한 승인 버전의 내용을 고정합니다. 과거 인계·외부 구현 사실은 현재 게이트 유효성과 구분합니다. 이미 전달된 파일의 회수나 외부 에이전트·테스트·배포의 자동 검증을 보장하지 않습니다.

## 5. 개발 완료 조건과 검증 증거

UOW-01의 개발 완료에는 다음 항목의 실제 실행 증거가 모두 필요합니다. 지금 완료했다고 표시하지 않습니다.

- 스토리 34개 각각의 모든 개별 기준과 지정된 공통 기준을 통과합니다. 연결된 FR·NFR·AC도 유지합니다.
- 행동 변경마다 예상한 RED를 확인하고 최소 구현으로 GREEN을 만든 뒤 관련 전체 검증을 통과합니다. 명령·exit code·결과를 기록합니다.
- 실제 저장의 재접속·실패 보존·이전 버전·권한·동시 변경·중복 요청·원자적 게이트와 인계를 확인합니다.
- 실제 Claude의 질문·문서·후속 생성부터 사람 적용·G1·G2·인계까지 AC-17을 검증합니다. 테스트 adapter만으로 통과 처리하지 않습니다.
- provider/model 교체 계약과 실행 제한·형식 오류·취소·늦은 결과·SR 분리를 AC-18·AC-19에 따라 검증합니다. 확인되지 않은 model ID를 추정하지 않습니다.
- 네 가상 SR의 보드·검토함·상세·이력과 주요 키보드 흐름을 확인합니다. 차단 이유와 담당자를 10초 안에 찾는지 관찰합니다. 검토함의 다음 행동 찾기와 승인 흐름도 별도로 확인합니다.
- 프로젝트 내부 자산을 별도 경로에서 실행·빌드·저장·재접속·내보내기 할 수 있는지 확인합니다. 설치 Claude와 기술 런타임의 명시적 전제는 실행 안내에 남깁니다.

가상 시작 상태는 개별 테스트에 사용할 수 있습니다. 미구현 쓰기 경로를 가짜 성공으로 대체한 결과를 실제 통합 통과로 집계하지 않습니다. Build and Test는 모든 단위 구현을 마친 뒤 실행하며 남은 단위 수용 기준을 미완료 상태로 넘기는 절차가 아닙니다.

| NFR Design | 트랜잭션·충돌·중복 방지·현재 조회·실행 소유권·취소 경합·재시작 복구·안전한 표시의 패턴입니다. |
| Infrastructure Design | 프로젝트 루트·저장·시드·PATH·설치 Claude·실행별 문맥·설정 격리·프로세스 종료·시작/재접속의 로컬 매핑입니다. |
| Code Generation | B-01부터 B-06까지의 실제 파일·테스트·검증 명령과 TDD 단계입니다. 구현 계획·결과 승인을 구분합니다. |
| Build and Test | 빌드·단위·계약·통합·성능·권한·UI·실제 Claude·프로젝트 사본 실행 안내와 확인 결과입니다. |

UOW-01에 대해 각 Construction 단계를 한 번씩 진행하고 B 묶음마다 단계 전체를 다시 시작하지 않습니다. 핵심 업무·원자성·AI 실행의 Comprehensive 깊이와 나머지 상세 수준은 승인된 실행 계획을 따릅니다. 현재 문서에서 기술 스택·OS별 종료 방식·수치를 임의 확정하지 않습니다.

## 7. 승인과 확장 상태

세 산출물을 독립 검토하고 모듈·계약·선행 관계·스토리·수용 기준·문서 경로의 일치를 검증했습니다. 정확한 명령과 결과는 `aidlc-docs/audit.md`에 있습니다. 이 문서는 단위 정의 산출물입니다. `aidlc-docs/inception/plans/unit-of-work-plan.md`의 Part 2 체크리스트로 생성·검증을 추적합니다. 단위 산출물 세 개를 승인받아 Construction의 Functional Design으로 진행합니다.

Security Baseline·Resiliency Baseline·PBT는 비활성 상태로 개별 규칙 N/A입니다. 전체 rule 로딩과 적용을 생략하며 기본 제품 NFR과 TDD는 유지합니다. 운영 인증·운영 배포·외부 레코드 변경·두 번째 실제 provider·설정 UI를 새 범위로 추가하지 않습니다.
