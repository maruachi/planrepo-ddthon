# PlanRepo 개발 단위 의존 관계

버전은 0.1이며 **사용자 승인 완료**입니다. 승인된 `aidlc-docs/inception/plans/unit-of-work-plan.md`를 따릅니다. 단위 정의는 `aidlc-docs/inception/application-design/unit-of-work.md`, 스토리별 완료 책임은 `aidlc-docs/inception/application-design/unit-of-work-story-map.md`에 있습니다. 모든 경로는 프로젝트 루트 기준입니다.

## 1. 단위 간 의존 행렬

행은 사용하는 단위이고 열은 제공하는 단위입니다. 개발 단위는 UOW-01 하나이며 단위 간 연결은 0개입니다.

| 사용 단위 / 제공 단위 | UOW-01 |
|---|---|
| UOW-01 | N/A |

자기 자신은 선행 단위가 아닙니다. N/A는 내부 의존이 없다는 뜻이 아니라 단위 간 자기 의존을 계산하지 않는다는 뜻입니다. 이 행렬에 Claude 프로세스·브라우저·DB·S 서비스를 추가 UOW로 넣지 않습니다.

## 2. 내부 모듈의 의존

아래 표는 승인된 `aidlc-docs/inception/application-design/component-dependency.md`의 관계를 연결합니다. UOW-01 안에서 사용 방향을 유지합니다.

| 사용하는 구성요소 | 사용하는 내부 구성요소 |
|---|---|
| C-01 | C-02 |
| C-02 | C-03, C-04, C-07, C-08, C-09 |
| C-03 | 없습니다. |
| C-04 | 없습니다. |
| C-05 | C-02, C-06, C-09 |
| C-06 | C-09 |
| C-07 | C-09 |
| C-08 | 없습니다. |
| C-09 | 없습니다. |

내부 연결은 11개입니다. C-01은 C-02의 공개 사용자 계약을 호출합니다. C-02는 정책·저장·Mock·표현·프로젝트 실행 기반을 사용합니다. C-05는 C-02의 내부 S-07 계약으로 영속 작업을 인수·조회·완료 처리하고 C-06을 실행합니다. C-06은 C-09의 제한 프로세스 실행을 사용합니다. C-02가 C-05를 직접 호출하는 의존을 추가하지 않습니다.

C-03은 순수 정책이며 파일·네트워크·DB를 읽지 않습니다. C-04는 유일한 영속 기준이고 C-08은 전달된 불변 자료를 표현합니다. 이 모듈들이 상위 사용자 서비스로 되돌아가 의존하지 않게 합니다. 공통 자료형과 composition root의 배치는 후속 기술 설계에서 이 방향을 유지하도록 정합니다.

### 반드시 함께 확정하는 변경

같은 업무 행동의 새 버전·현재 참조·ReviewImpact·현재 검토 요청·미해결 요청 승계·활동·receipt는 하나의 저장 경계에서 처리합니다. 모듈을 나눈다는 이유로 승인 무효화만 나중에 처리하는 비동기 저장으로 바꾸지 않습니다. B-01의 기반 위에 각 변경 경로를 추가할 때 이 경계를 검증합니다.

### 트랜잭션 밖의 생성 실행

생성 요청은 입력 스냅샷·ProviderSelection·대기 작업을 먼저 저장합니다. C-05는 S-07의 claimRun과 readRunControl로 자기 실행을 관리하고 취소를 ExecutionControl에 전달합니다. 완료/실패는 내부 결과 계약으로 저장하며 실제 종료 관찰은 recordExecutionTermination으로 별도 기록합니다. 늦은 관찰은 terminal 상태를 뒤집지 않습니다.

외부 provider는 명시 입력과 실행 제한만 받습니다. 업무 repository·승인 권한을 받지 않으며 AI 결과의 성공은 사람 적용과 다릅니다. 긴 실행 중에는 짧은 업무 트랜잭션을 점유하지 않아야 합니다.

## 3. 내부 구현 묶음의 선행 계약

다음 관계는 Code Generation 안에서 제공 기능을 준비하는 순서입니다. 각 묶음은 같은 UOW의 일부이고 독립 승인 단위가 아닙니다. 상위 Construction 단계의 설계·구현 계획 승인을 생략하지 않습니다.

| 묶음 | 선행 묶음 | 시작 전 필요한 조건 | 제공할 경로·증거 |
|---|---|---|---|
| B-01 | 없습니다. | 상세 설계와 Code Generation 계획이 승인돼야 합니다. | 루트 설정·가상 사용자·SR/근거·순수 정책·실제 저장 경계·버전/권한/중복 검사·초기 UI입니다. |
| B-02 | B-01 | SR·행위자·고정 입력을 저장하고 충돌·실패를 처리하는 실제 경로가 필요합니다. | 질문/답변/결정·문서 편집·사람 적용의 기본 경로, S-07 영속 작업, C-05 제어, C-06/09 실행·출력 계약과 초기 실제 Claude 증거입니다. |
| B-03 | B-02 | 편집·답변·초안 적용과 저장/ReviewImpact가 실제로 동작해야 합니다. | 질문 해결·전환·G1 묶음·개별 승인·수정 확인·G1 전환, 정책 버전·최초 배정과 관련 UI입니다. |
| B-04 | B-03 | 정확한 승인 G1과 질문·결정·수정 확인 경로가 필요합니다. | WorkflowPlan·설계·구현 계획·검증 연결, G2 묶음·검토·전환과 현재 조건 검사입니다. |
| B-05 | B-04 | 현재 유효한 G1/G2·문서·결정·검증 기준과 실제 생성/사람 적용 경로가 필요합니다. | 고정 Handoff·현재용 내보내기·외부 구현 사실·활동 조회와 AC-17 통합 증거입니다. |
| B-06 | B-05 | 초기 구현 경로와 현재/과거 인계·외부 사실·G1/G2 승인 상태가 준비돼야 합니다. | 승인 후 변경·G1/G2 무효화·새 배정·교체 이후 승인 절차·보드/검토함·생성 중 검토의 전체 검증입니다. |

선행 관계는 B-01에서 시작해 B-02, B-03, B-04, B-05, B-06 순서로 이어지며 연결은 5개입니다. 앞 묶음에서 구현한 기능의 전체 스토리 검증이 뒤 묶음에 배정돼 있어도 해당 기능의 실제 경로는 선행 조건으로 준비합니다. 예를 들어 B-03이 사용하는 답변·편집·초안 적용은 B-02에서 구현합니다. 이 기능의 승인 후 변경 검증은 B-06에 남습니다.

B-02는 최종 완료 스토리 수가 0개지만 실제 연결 검증과 후속 기능의 선행 구현을 담당합니다. 이를 선택 단계나 Mock만으로 대체 가능한 단계로 취급하지 않습니다. UI는 각 묶음에서 함께 연결하고 B-06에서 전체 상태의 일치를 확인합니다.

## 4. 시스템 전제와 외부 경계

| 대상 | 전제·책임 | 현재 확인 수준 |
|---|---|---|
| 설치 Claude | PATH로 찾아 공통 생성 계약 뒤에서 실행합니다. 요청 provider/model 선택을 고정하고 확인 가능한 실제 실행 정보만 기록합니다. | 설치·도움말 확인 이력만 있습니다. 실제 생성·인증·model 이용 가능성과 제한 효과는 미검증입니다. |
| 실행 제한 | 도구·MCP·설정·문맥·출력 상한·시간 제한·취소·프로세스 종료를 각각 검증합니다. | 수치·OS별 방법은 후속 NFR·Infrastructure Design에서 정합니다. |
| 로컬 런타임·저장 | 루트의 코드·설정·가상 자산으로 실행하고 데이터를 보존합니다. | 언어·프레임워크·DB는 아직 정하지 않았습니다. |
| Jira·GitHub | 프로젝트의 Mock 자료와 명시적인 외부 링크만 사용합니다. | 실제 API 쓰기·동기화나 외부 레코드 생성은 포함하지 않습니다. |
| 외부 구현 | 고정 인계를 사람이 전달하고 시작·완료 사실을 기록합니다. | 외부 코드·테스트·배포를 PlanRepo가 자동 확인했다고 표시하지 않습니다. |

설치 환경의 기본 model을 선택한 요청과 확인 가능한 실제 model ID를 구분합니다. 특정 ID의 사용 가능성을 추정하지 않습니다. 인증·전역 설정을 제품 코드가 임의 변경하도록 설계하지 않습니다. 테스트 provider의 성공은 실제 Claude 사용 가능성의 증거가 아닙니다.

## 5. 통합 검증 책임과 실패 처리

B-01부터 저장·현재 권한·무효화 기반을 검증하고 각 실제 변경 경로로 확대합니다. B-03·B-04는 게이트를 확정할 때 현재 권한·버전·묶음·필수 조건을 다시 검사합니다. B-05는 Handoff 생성과 현재용 내보내기를 같은 현재 유효성 원칙으로 확인합니다. B-06은 승인 후 변경과 재배정·이전 화면·늦은 생성 결과의 상호작용을 마무리합니다.

가상 시작 상태로 개별 정책을 검사할 수 있지만 실제 쓰기 경로를 가짜 성공으로 대체한 결과를 전체 통합 성공으로 보고하지 않습니다. 기본 정책 검사와 실제 저장 경쟁 검사도 구분합니다. 실패하면 해당 조건·현재 상태·검증 결과를 남기며 과거 저장본이나 승인을 덮어쓰지 않습니다.

초기 실제 생성이 막혀도 독립적인 저장·게이트 작업은 진행할 수 있습니다. 다만 실제 AI 수용 기준·관련 스토리·UOW의 완료는 미완료로 남깁니다. 이후 통합 검증은 선행 실제 경로가 준비됐을 때 실행하며 실패를 생략한 성공으로 집계하지 않습니다.

## 6. 문서 검증과 승인

검증 대상은 단위 1개의 행렬, 내부 구성요소 9개·연결 11개, B 묶음 6개·선행 연결 5개, 승인 계획과의 일치입니다. 별도의 Mermaid 그림은 추가하지 않았습니다. 기존 승인 그림과 위 행렬·글 설명으로 의존을 확인합니다.

이 문서의 생성은 실제 단위 구현 완료가 아닙니다. 세 산출물을 승인받아 UOW-01의 Functional Design으로 진행합니다. Security Baseline·Resiliency Baseline·PBT는 비활성 상태로 개별 규칙 N/A이며 기본 NFR·TDD는 유지합니다.
