# PlanRepo 작업 단위 의존성과 인계

상태: 승인된 분해 계획에 따라 작성. 산출물 Q1 A 승인 완료; 아래 인계 조건은 후속 구현에서 확인할 기준이다.

근거: [단위 정의](unit-of-work.md), [분해 계획](../plans/unit-of-work-plan.md), [컴포넌트 의존성](component-dependency.md), [서비스 흐름](services.md).

## 의존성 행렬

행은 의존하는 단위, 열은 선행 기반 단위이다. X는 개발/통합 선행 조건이며 별도 네트워크 서비스를 의미하지 않는다.

| 단위 | U1 | U2 | U3 |
|---|---|---|---|
| U1 | - | - | - |
| U2 | X | - | - |
| U3 | X | X | - |

실행 순서: U1 sr-document-foundation → U2 aidlc-planning → U3 review-implementation → 전체 Build and Test. 각 단위의 설계와 코드를 완료하고 다음 단위로 이동한다. 이 행렬은 단방향이며 순환 의존이 없다.

## 연결 경계

| 의존 관계 | 사용 계약·공유 자원 | 통합 담당과 제약 |
|---|---|---|
| U2 → U1 | SR/버전/사건 조회, C04.prepareGenerated, C09.read/commit, 앱 UI/전송 기반 | U2가 실행 결과와 문서 변경을 연결. U1에서 C05/C07/C08/C11 호출 없음 |
| U3 → U1 | 정확한 문서 버전 조회·이력·비교, C09 저장, C03·앱 기반 | U3가 Review와 사건을 추가하고 C03.markImplemented 구현 |
| U3 → U2 | 계획 진행 조건, 구현 대기 상태, 리뷰 문맥 읽기 계약 | U3가 실제 리뷰 중 진행·완료 연결 검증. C06이 C05/C11을 호출하는 구조는 아님 |

C01 → C02 → 서버 내부 서비스 → C09가 기본 조회/명령 흐름이다. 계획 실행은 C05가 C11·C07·C08을 조율하고 C04의 저장 전 변경을 C09에 전달한다. 리뷰는 C06이 C04·C09를 사용하며 계획 상태를 변경하지 않는다. 앱 조립 계층은 각 기능을 연결하지만 U1 도메인에서 후속 서비스를 역호출하지 않는다.

C07의 리뷰 문맥은 공통 저장 조회로 읽는다. U2는 리뷰 없음으로 동작하며 U3가 실제 Review 타입과 값을 연결한다. 이는 U2가 U3 구현을 선행 조건으로 요구하는 의존성이 아니다. C03.markImplemented 역시 저장 상태를 확인해 수동 전환하며 C05를 호출하지 않는다.

## 공유 자원과 변경 규칙

하나의 앱 서버·저장소·버전/사건 원본·빌드 설정을 공유한다. 별도 DB나 메시지 브로커를 추가하지 않는다. 후속 단위가 C09 스키마/타입을 확장할 때 U1에서 저장한 SR·문서·이력과 참조가 유지되는지 확인한다. 기존 공통 계약을 바꾸면 해당 설계 문서와 영향을 받는 검증을 함께 갱신한다.

CLI는 로컬 자식 프로세스로 호출한다. CLI를 기다리는 동안 저장 트랜잭션을 유지하지 않는다. 실행 시작 기록과 완료 저장은 별도이며 완료 시 문서·질문·Run·사건을 함께 반영한다. 저장 실패를 성공으로 공개하지 않는다. C08은 앱 저장소를 직접 수정하지 않는다.

| 인계 | 제공해야 할 결과와 증거 | 수신 단위의 확인 |
|---|---|---|
| U1 → U2 | SR/문서/버전/사건 계약, 저장 재열람, 편집/비교/복원과 과거 이력 보존, 저장 전 DocumentChanges, 공통 앱 실행 지침 | U2가 실제 생성 결과를 같은 저장 경계에 연결하고 입력 버전/늦은 결과 처리 검증 |
| U1 → U3 | VersionRef 소속 검증, 정확한 과거 본문 조회, 사건 조회·비교, 초기 데이터 보존 규칙 | 리뷰 대상을 원래 버전에 고정하고 최신과 구분; 역할에 따른 조회 재사용 |
| U2 → U3 | 단계·회차·자체 승인·구현 대기 계약, 실제 CLI 저장·열람과 실패 표시 증거, 리뷰 없음 문맥 | 실제 리뷰 요청 중 후속 계획 진행, 리뷰가 자체 승인을 대체하지 않음, 수동 완료 연결 |
| U3 → Build and Test | 역할 전환·버전 대상 결과·수동 완료, 모든 사건/카드 연결, 핵심 흐름의 실행 방법과 미해결 사항 | 전체 빌드, 통합 시나리오 하나, 실제 CLI 실패, 재열람·키보드 검증을 정리 |

인계 증거는 각 단위의 설계·코드 요약과 검증 기록에 남긴다. 준비 데이터 검증은 U1 계약 증거로 인정하지만 실제 AI 생성·리뷰 사건 생산을 검증했다는 기록으로 사용하지 않는다. 누락·실패가 있으면 완료로 표시하지 않고 해당 계약·구현을 수정한다.

## 통합 확인 순서

1. U1에서 SR 생성, 문서 편집·과거 버전 열람·비교·복원과 사건 보존을 확인한다.
2. U2에서 실제 CLI 생성·질문·응답·결정과 단계/회차를 연결하고 생성 중 편집·실패 경로를 확인한다.
3. U3에서 리뷰 대상 고정·미완료 리뷰 중 진행·자체 승인 구분·역할 전환·구현 대기에서 수동 완료를 확인한다.
4. 모든 단위 후 승인된 통합 시나리오와 실제 CLI 실패·키보드 조작·저장 재열람을 Build and Test에서 확인한다. 전체 E2E 자동화·성능 부하·PBT를 필수로 추가하지 않는다.
