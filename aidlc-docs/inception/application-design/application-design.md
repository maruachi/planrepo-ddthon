# PlanRepo 애플리케이션 설계

버전은 0.1이며 **사용자 승인 완료**입니다. 요구사항 0.4, 스토리·페르소나 0.1, 실행 계획 0.1을 승인받아 작성한 Application Design 산출물입니다. 사용자 응답 “응진행해”를 2026-09-08T13:49:54Z에 기록해 설계 0.1을 승인 처리했습니다.

## 1. 핵심 구성과 설계 범위

PlanRepo는 브라우저 UI, 로컬 백엔드와 영속저장으로 구성한 모듈형 앱을 제안합니다. 업무 모듈은 SR·질문·결정·문서·검토·게이트·정책·인계를 담당합니다. 별도 GenerationRuntime이 저장된 작업을 인수하고 제한된 Claude 자식 프로세스로 초안을 생성합니다. provider와 model은 공통 생성 계약 뒤에서 교체합니다.

원자적 변경이 필요한 승인·버전·요청·인계를 같은 로컬 저장 경계에서 처리하는 것이 이 구조의 핵심입니다. 여러 백엔드를 따로 배포하는 대안은 실행·복구·정합성 비용이 커 이번 한 팀 기능 데모에 채택하지 않습니다. 정확한 프레임워크·언어·DB 제품·OS별 실행 방법은 이후 설계에서 정합니다.

이 문서는 구성요소·서비스·입출력과 데이터 흐름을 통합합니다. 상세 상태 전이표·DB 스키마·잠금·CLI 제한 수치·최종 unit 분해는 후속 단계의 산출물입니다. 앱 코드나 실행 가능한 서버를 이번 단계에서 만들지 않습니다.

## 5. 저장·검토·생성의 전체 흐름

### 업무 변경

사용자 명령을 받은 서비스는 현재 상태와 정책을 확인합니다. 문서·결정·질문 처리 결과·정책·배정의 변경이 검토 기준에 영향을 주면 내용·검토 영향·현재 참조·요청 연결·활동을 함께 확정합니다. 별도의 나중 이벤트만으로 승인 무효화를 처리하지 않습니다.

불변 문서·결정·질문 결과·정책과 묶음 참조는 과거 기준을 보존합니다. 현재 묶음·상태·담당자는 별도로 관리합니다. 미해결 요청은 원 대상과 새 연결을 이어가며 삭제된 섹션의 요청도 별도 목록에서 보존합니다. 비차단 요청이 자동으로 게이트를 막지 않도록 차단 속성을 유지합니다.

### 사람의 검토와 게이트

공식 검토 요청은 고정 묶음 생성과 현재 검토 지정을 함께 처리합니다. 개별 승인과 단계 전환은 별도 명령입니다. G1·G2에는 지정 전원 승인과 담당자 외 동료가 필요하며 검토자 부재는 차단입니다. 역할을 겸임해도 각 행동의 배정 조건을 따릅니다.

G1 변경은 종속 G2와 신규 인계를 차단합니다. G2 전용 변경은 G1을 유지합니다. 새 차단 문제·필수 배정·정책 명시 적용 뒤에는 새 묶음과 재승인이 필요합니다. 문제 해결·G1 재승인만으로 과거 G2 승인을 복구하지 않습니다. 전환 확정 시 현재 조건을 다시 검사합니다.

### AI 실행과 사람의 적용

S-07은 SR·작업·내용·버전·근거 확인 상태·필요한 내부 규칙을 스냅샷으로 저장합니다. C-05는 영속 작업을 인수하고 C-06에 명시 입력과 실행 제한만 전달합니다. 외부 실행은 업무 트랜잭션 밖에서 일어납니다. 결과는 형식·참조·실행 소유권·현재 상태 검사 뒤 초안 또는 실패·취소 이력으로 저장합니다.

작업 성공은 초안이 생겼다는 뜻입니다. 입력이 바뀌면 stale로 표시하고 바로 적용하지 못하게 합니다. 사람의 applyDraft는 현재 입력·권한·문서 버전을 다시 확인하고 새 업무 버전·필요한 무효화를 함께 저장합니다. 질문·결정 제안도 사람의 반영을 거치며 결정 확정이나 공식 승인을 대신하지 않습니다.

실제 Claude와 테스트 provider는 같은 계약을 사용합니다. 요청 model과 확인 가능한 실제 model·CLI 버전은 구분하며 모르면 추정하지 않습니다. 연결 설정만 바꿔 기존 문서·승인을 변경하지 않습니다. 요청 시 고정한 provider·model 선택을 대기 이후 설정 변경으로 바꾸지 않습니다. 실행기는 내부 제어 조회로 취소를 전달하고 실제 종료 확인은 별도로 기록합니다. 취소·늦은 결과·재시도·복구를 제품 상태와 실제 프로세스 상태로 나누어 검증합니다.

### 인계·조회·외부 구현

Handoff는 유효한 G2가 참조하는 정확한 문서·결정·질문·승인·검증 기준·후속 범위를 고정합니다. 미리보기·Markdown은 같은 내용을 사용하고 현재용 내보내기 확정 시 게이트를 다시 검사합니다. 이미 전달된 파일을 소급 회수한다고 보장하지 않습니다.

보드·검토함·상세는 같은 확정 저장 상태에서 읽고 기준 revision을 표시합니다. 현재 할 일에서 이전 묶음 요청을 중복 표시하지 않습니다. 과거 승인·인계·외부 시작·완료 사실은 조회할 수 있으나 현재 유효한 승인과 혼동하지 않습니다. 외부 완료 근거가 있어도 PlanRepo가 외부 테스트·배포를 검증했다고 표시하지 않습니다.

## 8. 실제 CLI와 미검증 조건

이번에는 로컬 `claude --help`를 읽어 옵션의 설명만 확인했습니다. --tools 제한과 MCP 제한은 별개입니다. --safe-mode·--restricted의 설정 적용 범위와 --bare의 인증 차이도 구분했습니다. 어떤 옵션 조합이 실제 인증·생성·도구·MCP·문맥 격리를 충족하는지는 아직 실행하지 않았습니다.

현재 설치 인증과 권한을 임의로 바꾸지 않습니다. 기본 연결은 시스템 Claude이며 특정 model ID를 새로 보장하지 않습니다. 실제 실행 정책과 출력 포장 형식은 AI 단위의 초기 검증에서 확인합니다. 제한을 충족하지 못한 실행을 Mock 성공이나 완전한 격리라고 표시하지 않습니다.

| 후속 단계 | 구체화할 내용 |
|---|---|

## 9. 검토와 승인 상태

기본 구조는 단일 로컬 앱과 논리 모듈, 공유 저장 경계, 교체 가능한 제한 생성 adapter입니다. 프로젝트 안의 문서·시드·설정으로 재개·실행하도록 설계합니다. 운영 인증·배포·외부 레코드 변경·추가 실제 provider·자동 외부 에이전트 재개는 범위에 추가하지 않습니다.

독립 검토 두 건에서 찾은 계약 문제 5종을 수정하고 재검토를 마쳤습니다. 프로젝트/SR 요청 범위, 후속 분류 조건, 미승인 생성 입력, 취소 전달·종료 관찰, provider/model 선택 고정 시점을 보완했습니다. 구성요소 9개·서비스 9개·메서드 50개와 스토리 34개·FR/NFR/AC 50개 연결을 검증했습니다.

프로젝트 사본의 문서 21개·내부 참조와 Ruby RDoc Markdown 파싱, 의존 행렬·두 Mermaid의 작성 부분 문법·텍스트 대안, `git diff --check`를 검사했습니다. 정확한 명령·실패와 복구·최종 결과는 `aidlc-docs/audit.md`에 기록합니다. Mermaid renderer 화면·앱 구현·실제 생성·프로세스 제한·사용성 검증은 실행하지 않았습니다. 사용자 승인으로 Application Design을 완료했습니다.

Security Baseline·Resiliency Baseline·PBT는 비활성 상태로 N/A입니다. 기본 NFR과 사용자 지정 TDD는 계속 적용합니다. 이 승인에 따라 Units Generation으로 진행합니다.
