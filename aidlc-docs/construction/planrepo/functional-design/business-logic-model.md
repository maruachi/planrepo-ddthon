# PlanRepo 업무 논리와 상태 전이

버전은 0.1이며 **사용자 승인 완료**입니다. 승인 응답 “다음단계 진행”을 2026-09-08T14:53:15Z에 기록했습니다. UOW-01의 처리 순서·불변 조건·검증 시나리오를 정의합니다. 아래 표는 구현할 동작이며 현재 앱 테스트 통과 결과가 아닙니다.

## 1. 입력과 경계

기준은 `aidlc-docs/inception/requirements/requirements.md`, `aidlc-docs/inception/user-stories/stories.md`, `aidlc-docs/inception/application-design/component-methods.md`입니다. 엔티티는 `aidlc-docs/construction/planrepo/functional-design/domain-entities.md`, 규칙은 `aidlc-docs/construction/planrepo/functional-design/business-rules.md`, UI는 `aidlc-docs/construction/planrepo/functional-design/frontend-components.md`에 있습니다. SQL·HTTP·프로세스 명령·스택 선택은 이 문서에서 확정하지 않습니다.

### 공통 명령 알고리즘

1. 서버가 현재 가상 사용자·프로젝트·SR 범위를 해석합니다. 클라이언트 역할과 외부 출력의 승인 지시를 권한으로 사용하지 않습니다.
2. 저장 경계에서 대상 자원·현재 배정·버전과 중복 키를 읽습니다. 같은 범위·주체·키의 다른 명령 또는 입력은 충돌입니다. 같은 명령·입력의 receipt가 있으면 현재 권한을 확인합니다. 전환·현재용 인계에는 해당 현재 게이트·기준 유효성을 다시 검사합니다. 조건이 무효이면 Rejected와 이전 처리 정보를 구분해 반환합니다. 유효한 동일 요청은 Replayed로 즉시 반환하고 아래 쓰기 단계를 실행하지 않습니다. 과거 전환 사실의 재조회는 현재 단계를 바꾸지 않습니다. 첫 전환 뒤 출발 단계가 바뀌었다는 이유로 같은 전환을 다시 실행하지 않습니다.
3. 새 명령에만 행동별 권한, 기대 버전, 입력 구조와 참조 범위를 검사합니다. 묶음 승인에는 BundleRef·reviewEpoch·배정을 사용합니다. 다른 사람의 같은 묶음 승인으로 전역 SR revision이 달라졌다는 이유만으로 표를 거절하지 않습니다.
4. 새 불변 버전과 현재 포인터 변경안을 만듭니다. 변경의 게이트 범위, epoch, 재검토 단계, 요청 승계·대체와 활동·receipt를 계산합니다.
5. 같은 확정 경계에서 전부 저장합니다. 경쟁 변경이 있으면 현재 조건으로 다시 판단하거나 충돌을 반환합니다. 실패한 쓰기는 부분 승인·일부 무효화·성공 receipt를 남기지 않습니다.
6. 확정한 결과와 현재 기준을 반환합니다. 외부 호출은 경계 밖에서 수행하고 그 결과를 저장할 때 새 명령 경계의 검사를 거칩니다. 응답 유실은 실패로 단정하지 않고 같은 중복 키로 결과를 확인합니다.

일반 조회는 확정된 한 revision에서 읽고 업무 상태·검토 시작·활동을 변경하지 않습니다. 저장 직후 읽기 모델 갱신 실패를 새 업무 성공으로 꾸미지 않으며 최신 확정 상태를 다시 조회합니다.

### 검토 상태 표시 순서

위에서 먼저 맞는 행 하나를 선택합니다. G1/G2별로 계산한 뒤 SR은 현재 필요한 가장 앞선 게이트의 표시를 우선합니다.

| 순서 | 현재 조건 | 표시 |
|---|---|---|
| 1 | needsNewBundle이며 이전 공식 검토 기준이 있습니다. | 재검토 필요입니다. |
| 2 | 현재 사용할 공식 묶음이 없습니다. | 작성 중입니다. |
| 3 | 현재 범위의 미해결 차단 수정 요청이 있습니다. | 수정 필요입니다. |
| 4 | 현재 지정 검토자가 한 명 이상이고 전원의 현재 묶음 승인이 있습니다. | 승인 완료입니다. |
| 5 | 현재 묶음에서 검토자의 댓글·수정 요청·개별 승인 등 명시적 검토 행동이 있습니다. | 검토 중입니다. |
| 6 | 위 조건이 없고 현재 공식 묶음이 있습니다. | 검토 요청입니다. |

승인 완료 표시에도 질문·결정·동료 자격 등의 게이트 차단이 함께 보일 수 있습니다. 상세에는 “개별 승인 완료, 전환 조건 미충족”을 구분합니다. 페이지를 연 것만으로 검토 중이 되지 않습니다.

### 게이트 유효성과 묶음의 수명

처음은 not_passed입니다. 정식 전환이 통과한 현재 기준만 valid입니다. 기준 변경 시 과거 통과 기록이 있으면 invalid, 없으면 not_passed로 두고 needsNewBundle과 epoch를 따로 갱신합니다. 새 묶음 생성은 needsNewBundle을 해소하지만 통과 유효성을 자동 생성하지 않습니다. 같은 현재 내용·정책·배정·epoch로 M-020을 반복 요청하면 기존 현재 묶음과 요청을 반환합니다. 새 업무 요청 키여도 내용이 같은 묶음을 중복 만들거나 유효한 게이트를 불필요하게 되감지 않습니다. 기준이 달라진 경우에만 새 묶음을 만들고 변경 영향 처리를 거칩니다. 미해결 문제를 처리했다고 과거 묶음을 현재로 되돌리지 않습니다.

## 3. 순수 게이트 판정

판정은 아래 조건 목록과 차단 사유·담당자·대상 참조를 반환합니다. 값이 없는 배정·문서는 거짓이며 빈 집합의 전원 승인을 참으로 처리하지 않습니다.

| 조건 ID | G1 조건 | G2 조건 |
|---|---|---|
| GP-01 | 현재 공식 묶음이 현재 epoch·정책·배정·자료와 일치하고 needsNewBundle이 아닙니다. | 같습니다. |
| GP-02 | 요구사항의 범위·업무 규칙·완료 기준·예외·시스템/제약·근거 상태가 준비됐습니다. | 진행 계획·선택 필수 설계·구체적 구현 계획·요구사항/작업/검증 연결이 준비됐습니다. |
| GP-03 | converted_to_decision을 제외한 current, G1 필수 질문의 현재 답변·근거·반영 결과가 resolved입니다. | 전환 질문을 제외한 current의 G1과 G2 필수 질문 결과가 현재 기준에 맞습니다. |
| GP-04 | current, G1 필수 결정이 지정 결정권자의 현재 확정본이고 범위 변경 근거가 유효합니다. | current의 G1과 G2 필수 결정·범위 변경 근거가 유효합니다. |
| GP-05 | 현재 G1 범위의 차단 수정 요청이 모두 resolved입니다. | 현재 G1/G2 범위의 차단 수정 요청이 모두 resolved입니다. |
| GP-06 | 지정 집합이 비어 있지 않고 담당자 외 동료가 최소 한 명 있습니다. | 같습니다. |
| GP-07 | 지정 전원의 현재 BundleRef·epoch·체크리스트 승인이 있습니다. | 같습니다. |
| GP-08 | 정책의 필수 역할·체크리스트 조건이 충족됐습니다. | 같습니다. |
| GP-09 | 상위 게이트 조건은 N/A입니다. | 현재 G1이 valid이고 묶음의 g1BundleRef가 그 통과 기록과 정확히 같습니다. |

converted_to_decision 질문은 GP-03에서 제외하고 연결 결정을 GP-04에서 한 번만 검사합니다. 연결 결정이 없거나 같은 SR이 아니면 참조 오류로 차단합니다. 모든 적용 조건이 참이어야 통과합니다. 형식상 문서가 있다고 내용 준비까지 자동 인정하지 않습니다. 지정 검토자의 필수 체크리스트 확인과 구조화된 필수 필드·참조 검사를 함께 사용합니다. AI의 “완료” 문장은 조건이 아닙니다.

검토 요청의 준비 판정은 문서·참조·정책·배정 스냅샷 생성 가능 여부입니다. 아직 답하지 않은 필수 질문은 QuestionResultSnapshot, 확정 전 결정은 묶음 내부의 불변 unconfirmedDecisionSnapshots로 고정해 검토할 수 있습니다. 미해결 수정 요청은 묶음 본문을 수정하지 않고 별도 현재 상태·반영 이력을 연결해 보여줍니다. 따라서 개별 승인 API에 GP 전체를 적용하지 않습니다. 해결/확정으로 기준 내용이 달라지면 새 묶음과 그 기준의 승인을 요구합니다.

ReviewBundleView는 BundleAvailable 또는 NeedsInputs로 구분합니다. 전자는 고정 묶음·현재 여부·차단 상태를 반환합니다. 후자는 묶음 참조 없이 누락 자료·현재 배정/정책·다음 행동을 반환합니다. 최초 배정과 정책 적용 결과에 사용할 수 있습니다. requestReview 자체가 필수 입력 부족이면 묶음을 만들지 않고 검토 준비 오류를 반환합니다.

## 4. 변경 전파와 허용 전이

| 변경 종류 | G1 영향 | G2 영향 | 새 현재 인계 |
|---|---|---|---|
| G1 요구사항·필수 답변/해결·결정·범위·승인 근거 변경 | epoch 변경·새 묶음·재승인입니다. | 종속 기준도 무효이며 새 유효 G1로 검토합니다. | 차단합니다. |
| G2 전용 계획·설계·구현 계획·G2 필수 문제 변경 | 유지합니다. | epoch 변경·새 묶음·재승인입니다. | 차단합니다. |
| 새 필수 문제·차단 요청·검토자 변경·정책 명시 적용 | 관련 G1 조건이면 위 G1 변경과 같습니다. | G2만 관련되면 위 G2 변경과 같습니다. | 관련 게이트가 무효이면 차단합니다. |
| 일반 댓글·같은 자료 표시명·비차단 요청 추가 | 내용이 같으면 유지합니다. | 내용이 같으면 유지합니다. | 다른 조건이 유효하면 유지합니다. |
| AI 대기·성공 초안·실패·취소 | 적용 전에는 유지합니다. | 적용 전에는 유지합니다. | 다른 조건이 유효하면 유지합니다. |

변경 대상의 연결 범위를 확인할 수 없는데 현재 승인에 영향을 주는 자료이면 더 앞선 관련 게이트부터 재검토합니다. 영향 없는 메타데이터를 일괄 무효화하지 않습니다. 모든 미해결 요청은 차단 여부를 그대로 승계합니다.

| 현재 단계 | 명령과 조건 | 확정 단계 |
|---|---|---|
| sr_received | 담당자의 M-028이며 필수 등록 정보가 있습니다. | requirements입니다. |
| requirements | 담당자의 M-028이며 현재 G1 판정이 모두 참입니다. | planning이며 G1 통과 기록을 만듭니다. |
| planning | 담당자의 M-028이며 현재 G2 판정이 모두 참입니다. | ready이며 G2 통과 기록을 만듭니다. |
| ready | M-043이며 현재 유효 Handoff를 선택하고 외부 시작 근거를 기록합니다. | implementing이며 그 인계의 외부 기록을 활성 기준으로 선택합니다. |
| implementing | M-044이며 활성 인계의 완료 요약·근거, 현재 유효 게이트·인계가 맞습니다. | completed입니다. |
| planning, ready, implementing, completed | 이미 통과한 G1 기준이 바뀌었습니다. | requirements입니다. |
| ready, implementing, completed | G1은 유효하고 이미 통과한 G2만 바뀌었습니다. | planning입니다. |
| requirements | G2 변경도 발생했습니다. | requirements를 유지합니다. |
| 재검토 중인 단계 또는 다른 활성 인계 | 과거 인계의 M-044 완료 사실을 기록합니다. | 현재 단계를 유지하고 그 인계의 사실만 추가합니다. |

표에 없는 일반 전환·강제 이동은 거절합니다. M-028로 implementing/completed를 직접 선택할 수 없습니다. 재검토 전 외부 상태는 기록으로 남지만 재승인만으로 복구되지 않습니다. 현재 기준의 명시적 시작·완료 경로를 거칩니다.

### 범위 축소와 질문 반영의 순서

담당자가 범위 축소안을 준비하고 지정 결정권자가 변경 이유·영향을 확정합니다. 담당자가 요구사항·완료 기준을 개정해 참조를 연결하고 분류 버전을 저장합니다. 이때 이전 검토 기준은 무효이며 새 묶음의 질문/결정 목록은 변경 근거를 포함합니다. 새 묶음의 승인·전환에서 그 범위를 채택합니다. 초안 단계에서 미래 승인을 요구하지 않으며 기존 승인을 재사용하지 않습니다.

질문 답변은 이전 질문 정의 스냅샷에 답한 버전으로 저장합니다. 새 질문 결과 스냅샷이 그 답변을 가리킵니다. 담당자가 문서를 반영하거나 변경 불필요 이유를 확인한 뒤 resolved 스냅샷을 만듭니다. 새 답변 또는 관련 반영 변경은 예전 해결 확인을 무효로 만들고 재확인을 요구합니다. 관련 없는 문서 섹션 변경은 근거 변화로 단정하지 않습니다.

## 5. 생성과 초안 적용의 전이

| 현재 상태 | 사건·필수 조건 | 다음 상태 |
|---|---|---|
| pending | 내부 runtime의 단일 소유권 인수입니다. | running입니다. |
| pending | 현재 권한이 있는 취소가 먼저 확정됩니다. | cancelled입니다. |
| running | 현재 ClaimRef·상태·출력 검증이 맞고 성공이 먼저 확정됩니다. | succeeded입니다. |
| running | 현재 ClaimRef의 실패 또는 잘못된 출력이 먼저 확정됩니다. | failed입니다. |
| running | 현재 권한이 있는 취소가 먼저 확정됩니다. | cancelled입니다. |
| succeeded, failed, cancelled | 늦은 성공·실패·취소 사건입니다. | 기존 상태를 유지하며 현재 종료 결과를 반환합니다. |
| failed, cancelled | 재시도를 요청합니다. | 원 실행을 유지하고 새 pending 실행을 생성합니다. |

성공 결과가 오래되어 다시 생성하려면 M-032로 현재 입력의 새 요청을 만듭니다. M-035는 실패·취소 재시도 경로입니다. 중단 복구의 시간·재인수 방식은 후속 NFR 설계에서 정하지만 소유권이 끊긴 running을 영구 방치하거나 옛 실행의 늦은 결과로 현재 시도를 덮어쓰지 않는 조건은 고정합니다.

fingerprint의 업무 입력에는 작업 유형·보완 요청, 설명·자료의 버전/확인 상태, 질문 결과·결정·범위 분류, 참조 문서, 필요한 프로젝트 내 규칙의 내용/버전, 대상 문서의 정확한 버전 또는 명시적인 신규 대상 absent 기준이 포함됩니다. 최초 문서 생성은 이전 버전 없이 가능하며 적용 전에 같은 논리 대상이 생기면 INPUT_CHANGED로 거절합니다. provider/model 선택은 실행별로 별도 고정합니다. 요청 후 기본 설정이 바뀌었다는 이유만으로 동일한 업무 입력 결과를 오래되게 만들지 않습니다.

완료 시 현재 입력과 다르면 초안을 stale로 보존합니다. 적용 시 다시 비교하므로 완료 후 변경도 탐지합니다. 사람의 검토 초안은 원 run/draft와 현재 입력을 연결하고 다시 적용 검사를 받습니다. 초안 하나의 적용은 최대 한 번이며 같은 적용의 반복은 같은 결과를 반환합니다. 새 선택·추가 비교는 새 초안에서 처리합니다. 한 적용이 여러 미확정 질문·결정을 만들 수 있지만 답변·확정·승인을 대신하지 않습니다.

취소 요청과 실제 종료 관찰은 다릅니다. M-049와 M-050은 같은 ClaimRef의 종료 제어/관찰이며 terminal 상태에서도 종료 사실만 다룰 수 있습니다. UI에 프로세스가 끝났다는 관찰 없이 종료 완료라고 표시하지 않습니다.

## 6. 논리 메서드와 처리 흐름

### FL-01 작업 공간·SR·자료

계약: M-001, M-002, M-003, M-004, M-005, M-006, M-007. 규칙: BR-01, BR-02, BR-03, BR-10, BR-12.

### FL-02 질문·결정·범위

계약: M-008, M-009, M-010, M-011, M-012, M-013, M-014. 규칙: BR-04, BR-05, BR-06, BR-07.

### FL-03 문서·진행 계획·비교

계약: M-015, M-016, M-017. 규칙: BR-08, BR-09, BR-11, BR-12, BR-19, BR-20.

현재 문서 버전과 안정적인 ID를 검사하고 새 원문·색인·변경 요약을 만듭니다. 삭제·변경 섹션의 미해결 요청을 연결하고 ReviewImpact와 함께 확정합니다. 비교는 두 불변 원문과 구조 변경을 읽으며 새 문서나 검토 상태를 쓰지 않습니다.

### FL-04 공식 검토·개별 승인

계약: M-020, M-021. 규칙: BR-13, BR-15, BR-16, BR-19.

검토 입력 준비를 확인해 묶음·정책·배정·epoch를 고정합니다. 현재 검토 요청을 배정하고 이전 요청을 대체합니다. 각 검토자는 이 묶음과 체크리스트를 확인해 자신의 승인만 기록합니다. 승인 수는 조회에서 집계하며 전원 승인만으로 단계나 gateValidity를 바꾸지 않습니다.

### FL-05 댓글·수정·확인

계약: M-022, M-023, M-024, M-025, M-026. 규칙: BR-10, BR-17, BR-18, BR-19, BR-20.

댓글은 버전·섹션에 연결합니다. 수정 요청은 원 요청자·담당자·차단 여부를 보존합니다. 반영 제출은 현재 반영 버전과 근거를 고정해 확인 대기로 만듭니다. 원 요청자 또는 현재 지정 검토자가 정확한 현재 결과를 확인하거나 추가 수정을 요청합니다. 차단 요청이 해결되어도 오래된 묶음은 복구하지 않습니다.

### FL-06 게이트 평가·단계 전환

계약: M-027, M-028. 규칙: BR-16, BR-20, BR-21, BR-22.

조회는 아래 순수 게이트 판정 결과를 제공합니다. 명령은 현재 스냅샷에서 다시 평가하고 허용 전이만 확정합니다. G1 통과는 planning, G2 통과는 ready로 바꿉니다. 이전 재검토보다 뒤의 상태로 자동 복귀시키지 않습니다.

### FL-07 팀 정책·검토자

계약: M-029, M-030, M-031. 규칙: BR-10, BR-14, BR-20, BR-30.

관리자가 새 정책 버전을 만듭니다. SR별 배정·정책 명시 적용은 해당 기준을 바꾸고 이전 요청을 대체합니다. 문서가 준비되면 새 묶음을 함께 만들고 미준비이면 배정/적용은 저장하되 누락 입력을 반환합니다. 새 기본 정책 생성만으로 기존 SR을 변경하지 않습니다.

### FL-08 생성 요청·조회·취소·재시도

계약: M-032, M-033, M-034, M-035. 규칙: BR-23, BR-24, BR-25, BR-27.

서버가 현재 저장된 입력과 provider/model 선택을 고정해 pending 작업을 만듭니다. 조회는 작업 상태·입력·초안·오래됨·적용·종료 확인을 나눠 보여줍니다. 취소는 업무 terminal 상태를 먼저 경쟁 확정하고 runtime이 별도로 신호·실제 종료를 관찰합니다. 재시도는 현재 입력으로 새 실행을 만들며 과거 실행을 유지합니다.

### FL-09 내부 생성 실행

계약: M-036, M-037, M-038, M-039, M-049, M-050. 규칙: BR-01, BR-24, BR-25, BR-27.

runtime이 단일 ClaimRef로 pending 작업을 인수합니다. 업무 저장 경계 밖에서 고정 입력만 provider에 전달합니다. 완료 시 소유권·상태·결과 구조·SR 참조를 검사하고 초안 또는 정제한 실패를 확정합니다. 중단 복구는 소유권이 끊긴 running을 방치하지 않습니다. 종료 관찰은 같은 ClaimRef의 사실만 기록하며 terminal 상태를 뒤집지 않습니다.

### FL-10 사람의 초안 검토·적용

### FL-11 인계·외부 구현

계약: M-045, M-046, M-047, M-048. 규칙: BR-30, BR-31, BR-32.
