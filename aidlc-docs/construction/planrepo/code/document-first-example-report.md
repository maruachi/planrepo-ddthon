# 문서 중심 프로토타입과 배송 전 취소·환불 예시

기준 시각은 2026-09-09T06:05:25Z입니다. 등록 원문을 읽고 직접 수정하는 흐름을 기본으로 바꿨습니다. 배송 전 머그컵 주문 취소 예시를 실제 로컬 앱에서 문서 v3 최종 승인까지 진행했습니다.

## 실제 사람이 하는 일

작성자는 가지고 있던 초안과 검토자를 등록합니다. 본문을 직접 다듬거나 AI의 추천을 선택합니다. 중요한 업무 원칙과 승인 범위는 사람이 판단합니다. 검토자는 같은 문서를 읽고 수정 요청을 남기며, 수정본을 확인한 뒤 승인합니다.

시스템은 문단 구조, 문서 버전, 수정 요청 연결, 현재 검토 대상과 승인을 관리합니다. AI 질문을 모두 완료하거나 별도 근거 칸을 채우는 일은 승인 조건이 아닙니다. 문서에 없는 주장을 실제 사실로 인정하는 자동 승인은 하지 않습니다.

## 화면과 동작

- 등록 원문을 그대로 첫 Plan 문서로 저장합니다. 여섯 문서나 정해진 제목이 없어도 비어 있지 않은 문서로 검토를 시작할 수 있습니다.
- 상세 화면은 문서, 요약·시각화, 공유·리뷰의 세 탭입니다. 처음에는 전체 문서 본문을 보여 줍니다.
- AI 기능은 접힌 선택 영역입니다. 문서 편집 입력에는 본문만 표시합니다. 시각화 메타데이터와 문단 연결은 시스템이 보존합니다.
- 검토 요청 버튼 한 번으로 필요한 내부 상태 전환과 검토본 생성을 처리합니다.
- 수정 반영은 바꾼 내용만 입력합니다. 확인 근거는 현재 문서 버전과 실제 연결 문단에서 자동 구성합니다.
- 검토자는 선택 메모와 수정 내용 확인 버튼으로 응답합니다. 추가 수정도 한 번만 입력합니다.
- 문서 시각화에서 문서로 이동하면 관련 문단으로 스크롤합니다. Markdown 표를 읽기 쉬운 표로 렌더합니다.
- 검토자 배정 폼은 기본 접힘으로 표시합니다. 최종 승인은 현재 문서 버전의 검토 결과와 연결합니다.

## 예시에서 실제 진행한 내용

예시 제목은 [예시] 배송 전 주문 취소·환불입니다. SR 식별자는 sr-1a3cf4a3-377e-45ee-8f4d-c158fad36e69이며 로컬 화면의 업무 번호는 SR-SQPKHL입니다.

1. 초안과 동료 검토자를 등록했습니다.
2. 설치된 Claude로 참고 질문과 Plan 초안을 생성했습니다. 두 실행이 모두 succeeded입니다.
3. 취소와 배송이 겹칠 때 먼저 확정한 주문 상태를 유지한다는 예시 정책을 답했습니다.
4. AI 초안을 읽고 문서 v2로 적용했습니다. 별도 질문 반영 확인 명령은 사용하지 않았습니다.
5. 검토자 역할로 문단 댓글과 수정 요청을 남겼습니다. 배송 우선이라는 표현의 오해와 고객 안내 문구 부족을 지적했습니다.
6. 담당자 역할로 직접 문서 v3를 저장했습니다. 중요한 결정의 표현, 네 상황의 화면 문구, 완료 판단 표, 구성요소 설명을 다듬었습니다.
7. 수정 결과를 보내고 검토자 역할로 해결을 확인했습니다.
8. 현재 문서로 다시 검토를 요청했습니다. 동료 검토자 승인 후 담당자가 최종 승인했습니다.

로컬 체험 역할을 전환해 진행한 시연입니다. 실제 직원의 결재나 실제 주문·환불 실행은 아닙니다. 39,000원, 3~5영업일, 30분 알림은 예시의 가정입니다.

최종 조회 결과는 문서 v3, 현재 검토 유효, 수정 요청 resolved, 승인 1건입니다. 참고 질문은 answered 상태 그대로입니다. 내부 progressStage는 planning이며 현재 UI에서는 문서 결재 완료로 표시합니다. Construction이나 개발 실행을 요구하지 않습니다.

원본 Plan과 앱의 최종 Markdown은 정확히 같습니다. 문서 묶음은 aidlc-docs/examples/delivery-cancel/README.md에서 읽습니다. 실제 조회 결과와 화면은 같은 폴더의 evidence에 있습니다.

## 승인 후 차단 문제

기존 상품 검색 필터 업무는 검토자 전원이 현재 검토본을 승인했지만 열린 질문 때문에 최종 전환만 막혔습니다. 사용자 데이터를 바꾸지 않고 이 상태를 확인했습니다.

현재 실행은 명시적인 documentReviewMode를 사용합니다. G1에서 참고 질문과 미확정 결정 기록은 강제 완료 대상이 아닙니다. 실제 문서, 지정 검토자, 현재 버전 승인, 사람이 남긴 미해결 수정 요청은 계속 확인합니다. 일반 계약과 기존 엄격 모드는 유지합니다.

수정 뒤 같은 기존 업무의 canTransition은 true입니다. 질문 두 개는 open 상태를 유지했습니다. 다른 업무를 대신 수정하거나 승인하지 않았습니다.

## Claude 실행 중단 원인

생성이 가능한 환경에서도 유휴 실행 루프의 SQLite 쓰기 경합 한 번이 worker를 종료시켜 generationReady가 false가 됐습니다. claim 단계의 SQLITE_BUSY만 제한적으로 재시도하도록 수정했습니다. 250ms 잠금에서 준비 상태를 회복했고 지속 잠금 실패는 숨기지 않습니다.

빌드에는 기존 Vite 차기 설정 로더 안내와 500kB 초과 chunk 경고가 남았습니다. 전체 제품 E2E·성능 검사와 포괄적인 TDD 확장은 사용자 프로토타입 범위에 따라 생략했습니다.

## 실패한 보조 확인과 수정

초기 worker는 SQLITE_BUSY로 중단됐으며 재시작과 제한 재시도로 수정했습니다. 보조 확인 중 잘못된 manifest 경로, 조회 결과의 state/status 혼동, 아직 끝나지 않은 문서 쓰기 뒤 조기 읽기, 브라우저의 이전 ref 재사용과 viewport 인자 형식 오류가 있었습니다. 올바른 경로·status·쓰기 완료 대기·새 selector·390x844 형식으로 다시 확인했습니다. Markdown 렌더 probe는 실제 웹 tsconfig를 지정한 뒤 통과했습니다.

중간 웹 타입 검사는 병렬 작성 중인 파일 때문에 실패했습니다. 모든 변경을 합친 최종 타입 검사는 통과했습니다. 앞선 실패를 통과 결과로 간주하지 않았습니다.
