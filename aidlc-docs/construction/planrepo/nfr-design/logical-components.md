# PlanRepo 비기능 논리 구성요소

버전은 0.1이며 **사용자 승인 완료**입니다. 승인 응답 “어 진행해도될거같아”를 2026-09-08T15:50:03Z에 기록했습니다. 승인된 NFR Requirements 0.1을 단일 UOW-01의 구현 책임에 연결합니다. LC-01부터 LC-12까지는 기존 모듈 내부의 협력 책임이며 새 서비스·공개 API·배포 단위를 뜻하지 않습니다. 이 문서는 구현·패키지 설치·DB 실행·실제 Claude 검증 결과가 아닙니다.

## 2. 논리 구성요소

### LC-01 공개 요청과 내부 계약의 전송 경계

- **소유와 책임**: C-09 실행 구성에서 조립하는 얇은 전송 계층과 C-02의 서비스 진입 계약입니다. Fastify는 요청의 구조·크기를 검사하고 공개 호출을 C-02로 전달합니다. 가상 사용자 선택을 실제 조직 인증으로 표현하지 않습니다.
- **입출력과 메서드**: CommandContext·QueryContext와 업무 입력을 받아 Committed·Replayed·Rejected 또는 조회 결과를 반환합니다. 공개 범위는 M-001부터 M-035, M-040부터 M-048까지 44개입니다. M-036, M-037, M-038, M-039, M-049, M-050은 브라우저용 경로에 등록하지 않습니다.
- **저장·실행 경계**: 서버가 ActorContext와 ProjectScope 또는 SrScope를 확인합니다. 요청 스키마 검사는 현재 역할·배정·참조 검사나 업무 트랜잭션을 대신하지 않습니다. 사용자·AI가 제공한 schema를 실행 가능한 validator로 등록하지 않습니다. 구체적인 HTTP 경로·origin·시작 배치는 Infrastructure Design에서 정합니다.
- **실패 처리**: 요청 크기 초과·입력 오류·권한 부족·저장 실패를 성공 응답으로 바꾸지 않습니다. 응답 유실은 이전 요청의 동일 키 재확인으로 처리하고 새 쓰기를 자동 재실행하지 않습니다. CLI 부재는 실제 생성만 PROVIDER_UNAVAILABLE로 실패시키며 비AI 경로를 막지 않습니다.
- **추적과 검증**: NQ-02, NQ-04, NQ-07, NQ-08, NQ-10, NQ-17, NQ-22, NQ-23, NQ-24입니다. 공개/내부 계약 분리, 직접 요청 권한 검사와 전송된 JSON bytes의 경계를 검증합니다.

- **입출력과 메서드**: 현재 저장 스냅샷과 명령을 받아 업무 변경안·GateAssessment·ReviewImpact 또는 DomainError를 반환합니다. SR/근거는 M-003, M-004, M-005, M-006, M-007이며 질문/결정/범위는 M-008, M-009, M-010, M-011, M-012, M-013, M-014입니다. 문서/계획은 M-015, M-017이고 검토는 M-020, M-021, M-022, M-023, M-024, M-025, M-026, M-027, M-028입니다. 정책/배정은 M-029, M-030, M-031이며 인계/외부 사실은 M-040, M-042, M-043, M-044입니다. 생성·적용 명령도 같은 현재 권한 정책을 사용합니다.
- **저장·실행 경계**: C-02가 LC-03의 짧은 확정 경계 안에서 현재 조건을 읽고 C-03의 순수 판단을 적용합니다. C-07의 승인된 Mock 조회 결과는 경계 밖에서 준비하고 저장 시 중복·범위를 다시 확인합니다. 새 버전·무효화·가장 앞선 재검토 단계·미해결 요청 승계·활동·receipt는 함께 확정합니다.
- **실패 처리**: 범위 축소의 사람 결정과 개정 기준, 전환 질문의 재답변 금지, 지정 결정권자와 원 요청자의 확인 자격을 유지합니다. G1 변경은 종속 G2도 무효화하고 G2 전용 변경은 G1을 보존합니다. 같은 기준의 M-020은 기존 묶음·요청을 재사용합니다. H1 완료는 H2나 현재 SR을 잘못 완료시키지 않습니다.

### LC-03 SQLite 원자적 확정과 영속 기록

- **소유와 책임**: C-04의 TransactionBoundary·업무 repository·RunRepository·ReceiptRepository입니다. 하나의 영속 기준에 불변 내용과 현재 참조, 작업·실행 관찰·활동·중복 처리 결과를 보존합니다.
- **입출력과 메서드**: C-02가 전달하는 withinTransaction 작업과 저장 변경을 받아 확정 결과 또는 저장 오류를 반환합니다. 별도 공개 M 메서드는 없으며 LC-02·LC-05·LC-06·LC-09의 변경과 M-050 종료 관찰을 뒷받침합니다.
- **저장·실행 경계**: 단일 연결의 짧은 동기 트랜잭션은 async 작업을 포함하지 않습니다. 외래 참조·범위·기대 버전·고유 키를 검사하고 commit 후에만 성공을 반환합니다. idempotency 범위는 TargetScope·actor·key입니다. 동일 키의 다른 명령/입력은 충돌입니다. 같은 receipt는 현재 권한과 전환/현재용 인계 조건을 검사한 뒤 Replayed로 즉시 반환합니다. 재생은 새 쓰기의 기대 버전을 다시 적용하거나 활동을 추가하지 않습니다.
- **실패 처리**: 중간 실패는 전체 rollback이며 메모리 저장으로 자동 전환하지 않습니다. commit 뒤 응답이 유실돼도 동일 receipt로 이전 처리 사실을 확인합니다. 이미 저장된 원문·승인·인계는 변경 실패로 훼손하지 않습니다. 잠금 대기·오류 분류·실제 내구성은 정해진 측정 조건에서 확인합니다.
- **추적과 검증**: NQ-02, NQ-04, NQ-05, NQ-06, NQ-07, NQ-08, NQ-09, NQ-14, NQ-21, NQ-22, NQ-24입니다. 실제 SQLite의 저장 중 장애·commit 전후 장애·동시 명령·재개방 검사를 담당합니다.

### LC-04 같은 확정 기준의 조회

- **소유와 책임**: C-02의 S-09와 관련 조회 서비스, C-04의 ReadRepository·readConsistent입니다. C-03의 정책 판단과 C-08의 표현 결과를 C-02가 조합합니다. C-04에서 상위 모듈을 호출하지 않습니다.
- **입출력과 메서드**: actor·ProjectScope/SrScope·필터·대상 버전을 받아 현재 revision이 연결된 조회 결과를 반환합니다. M-001, M-016, M-027, M-033, M-041, M-045, M-046, M-047, M-048입니다.
- **저장·실행 경계**: 한 응답의 보드·검토·차단·외부 사실은 한 저장 스냅샷을 사용합니다. 짧은 일관된 읽기로 자료를 고정하고 비용이 큰 비교·표현은 불변 입력을 받은 뒤 처리합니다. 초기에는 서버의 별도 업무 결과 캐시를 두지 않습니다. 조회는 숨은 승인·검토 시작·활동 쓰기를 만들지 않습니다.
- **실패 처리**: 저장소 오류를 빈 목록으로 숨기지 않습니다. 과거 인계와 현재 유효성을 따로 반환하고 조회 결과를 전환 권한으로 재사용하지 않습니다. 페이지·필터 범위가 바뀌어도 같은 SR의 상태 축을 다른 revision에서 합성하지 않습니다.
- **추적과 검증**: NQ-01, NQ-02, NQ-03, NQ-04, NQ-09, NQ-10, NQ-13, NQ-24입니다. 변경과 조회를 교차 실행해 상태 혼합·중복 검토함·조회로 인한 쓰기를 검사하고 PERF-100에서 측정합니다.

### LC-05 입력 스냅샷과 사람의 초안 적용

- **소유와 책임**: C-02의 S-07이 생성 입력을 고정하고 S-04가 사람의 비교·적용을 담당합니다. C-03이 현재 권한·검토 영향을 판단하고 C-04가 자료를 보존합니다.
- **입출력과 메서드**: M-032와 M-035는 현재 입력으로 InputSnapshot·ProviderSelection·pending Run을 만듭니다. M-019는 사람의 현재 비교 초안을 만들고 M-018은 명시적 선택을 새 문서 또는 미확정 질문·결정으로 적용합니다.
- **저장·실행 경계**: 입력은 SR·workflowVersion·문서/질문/답변/결정/근거의 내용·버전·확인 여부·필요 로컬 규칙과 provider/model 선택을 포함합니다. 새 문서의 absent 기준과 기존 문서의 정확한 VersionRef를 구분합니다. 큰 직렬화를 저장 경계 밖에서 준비하면 확정 전에 입력 기준을 다시 확인합니다. 대기 중 설정 변경으로 저장된 선택을 교체하지 않습니다.
- **실패 처리**: 입력 초과는 조용히 생략하지 않습니다. 완료와 적용 시 fingerprint·대상 기준을 각각 비교합니다. 오래된 성공은 보존하되 즉시 적용을 거절합니다. 사람의 새 비교 초안도 현재 기준에 연결하며 같은 초안은 한 번만 적용합니다. 초안 적용으로 질문 해결·결정 확정·승인·단계 전환을 자동 처리하지 않습니다.
- **추적과 검증**: NQ-06, NQ-07, NQ-08, NQ-10, NQ-17, NQ-18, NQ-20, NQ-24입니다. 미확정 입력 보존·설정 변경·absent 생성 경쟁·동시 적용·재검토 계보를 계약/실제 저장 테스트로 확인합니다.

### LC-06 영속 대기열·인수·상태 경쟁

- **소유와 책임**: C-02의 S-07이 상태를 관리하고 C-04가 Run·ClaimRef에 연결된 저장 사실을 보존합니다. C-05는 내부 계약을 호출하는 실행 주체이며 DB를 직접 읽거나 고치지 않습니다.
- **입출력과 메서드**: M-032, M-033, M-034, M-035와 내부 M-036, M-037, M-038, M-039, M-049, M-050을 연결합니다. 인수 결과는 고정 입력·선택·실행 제한·ClaimRef를 가진 ClaimedRun입니다.
- **저장·실행 경계**: 신규 접수·용량 검사·receipt를 원자적으로 처리합니다. nonterminal 총 10개와 실제 생성 1개 제한을 별도로 검사합니다. 같은 DB의 실행 슬롯을 원자적인 조건부 갱신으로 인수해 앱 프로세스가 둘이어도 실제 실행이 겹치지 않게 합니다. 프로세스 메모리의 running 표시만으로 슬롯을 판단하지 않습니다. running이 없으면 pending 10개까지 가능하지만 종료 미확인 실행이 있으면 인수하지 않습니다. 인수는 pending에서 한 번만 가능하며 terminal·중단 Run을 같은 실행으로 다시 인수하지 않습니다.
- **실패 처리**: 성공·실패·취소는 먼저 확정된 terminal을 보존합니다. M-049와 M-050은 terminal 뒤에도 원 ClaimRef의 제어 조회·종료 관찰만 허용합니다. M-050은 현재 슬롯의 ClaimRef가 관찰한 실행과 같을 때만 슬롯을 해제합니다. 과거 종료 관찰의 중복 전달로 다른 실행의 슬롯을 지우지 않습니다. 복구는 끊긴 running을 중단 실패로 분류하되 종료 미확인을 지우지 않습니다. 기존 pending은 보존하고 종료가 확인된 빈 슬롯에서 각 Run을 처음 인수합니다. 중단된 running을 자동 재실행하지 않습니다. 재시도는 사용자가 요청한 현재 입력의 새 Run입니다.
- **추적과 검증**: NQ-02, NQ-06, NQ-08, NQ-14, NQ-15, NQ-16, NQ-21, NQ-22, NQ-24입니다. 두 실행기의 인수 경쟁·11번째 접수·포화 시 조회/취소·재시작·늦은 원 실행 결과·첫 terminal 보존을 실제 저장과 제어 가능한 adapter로 확인합니다.

### LC-07 프로세스 소유권·취소·종료 관찰

- **소유와 책임**: C-05가 실행 수명과 내부 S-07 호출을 관리합니다. C-09의 ControlledProcessRunner는 제한 실행·프로세스 핸들·입출력·시각 관찰의 기반을 제공하고 C-06은 그 기반으로 provider를 실행합니다.

4. **초안의 사람 적용**: LC-11이 결과의 출처·오래됨·현재 입력을 보여줍니다. LC-05는 필요한 M-019 비교 초안과 M-018의 명시적 적용을 처리합니다. 적용 직전 현재 입력·대상·권한·한 번 적용 여부를 검사하고 일반 업무 변경과 같은 원자성·재검토 규칙을 사용합니다.
5. **고정 인계와 외부 사실**: LC-02가 M-040에서 유효 기준을 확인하고 LC-10이 정확한 Markdown을 구성합니다. 고정된 인계는 LC-03이 보존합니다. M-041은 과거 내용과 현재 유효성을 함께 보여주며 M-042는 현재 조건을 다시 검사한 뒤 같은 고정 bytes를 내보냅니다. M-043/M-044의 외부 사실은 선택한 Handoff에만 연결합니다.
6. **독립 시작과 비AI 이용**: LC-12가 프로젝트 자산과 실제 저장소 준비 상태를 구분합니다. CLI가 없어도 LC-01부터 LC-04와 LC-10/LC-11의 비AI 기능은 이용할 수 있습니다. Claude 이용 가능·실제 생성 성공·실행 격리 검증은 서로 다른 증거로 남깁니다.

## 6. 후속 설계와 미검증 경계

단일 연결·DELETE/FULL의 응답시간과 crash 보존, 정확한 native 패키지·내장 SQLite 버전, Markdown 변환 경로와 표시 정책은 실제 검증이 남아 있습니다. 긴 동기 작업이 취소 신호와 API 지연 목표를 막는지 측정하고 조용히 수치를 낮추지 않습니다.

프로세스 실행 프로파일·인스턴스 소유권·부모 중단 후 원 자식 종료의 신뢰 가능한 확인·OS별 정리·입출력 상한의 실제 효과는 후속 설계와 초기 실행으로 검증합니다. 미확인 종료를 확인으로 바꾸거나 PID만으로 다른 프로세스를 종료하지 않습니다. 확인 수단을 확보하지 못한 환경은 새 생성이 막힌 상태로 남기며 실제 AI 수용 기준을 완료로 표시하지 않습니다.

이 문서 승인 시점에는 실제 코드·패키지 설치·DB·브라우저·Claude 실행을 하지 않았습니다. 이후 2026-09-09에 기존 설치 환경의 짧은 실제 Claude 호출과 모델/provider 확인을 마쳤습니다. 앱 통합·AC-17 전체·취소·timeout·복구·전체 격리 검증은 남아 있습니다. Security Baseline·Resiliency Baseline·PBT 확장은 비활성으로 적용을 생략했고 준수 판정은 N/A입니다. 승인된 기본 NFR·권한·AI 경계와 TDD를 유지합니다.
