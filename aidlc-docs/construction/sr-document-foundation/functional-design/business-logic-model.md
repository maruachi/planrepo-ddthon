# U1 업무 처리 모델

상태: 기능 설계 Q1 B 승인 완료. [도메인](domain-entities.md)과 [업무 규칙](business-rules.md)을 함께 적용한다. [설계 계획](../../plans/sr-document-foundation-functional-design-plan.md)의 U1 범위를 따른다.

## 책임과 데이터 흐름

브라우저 C01은 C02에 명시적인 조회/사용자 명령을 전달한다. C02는 C03 SRService 또는 C04 DocumentService를 호출한다. C03은 C10으로 입력을 정규화한다. C03/C04는 C09에서 조회하고 서버 내부 ChangeSet을 저장한다. C09의 확정된 응답 이후에만 UI가 저장 성공을 표시한다.

U1에서 후속 C05/C06/C07/C08/C11 서비스를 호출하지 않는다. AI 생성은 U2가 C04.prepareGenerated의 저장 전 결과를 받아 실행 결과와 함께 커밋한다. 여기서 C04는 AI를 실행하지 않는다.

## 흐름 1: SR 생성과 재열람

1. 입력 폼이 제목·설명·선택 첨부를 SRDraft로 전달한다. 서버에서 C10 검증을 다시 수행한다.
2. C03이 SRId, 초기 sr_list 상태 및 sr_created 사건을 준비한다.
3. C09가 한 변경으로 확정한다. 실패하면 카드·사건을 일부만 공개하지 않는다.
4. 성공한 SRId로 상세를 열고 보드를 다시 읽는다. 다른 화면을 거쳐도 저장된 초기 입력을 조회한다.

처음에는 문서 0개가 정상이다. U1 시연을 위해 가짜 AI 성공 문서를 자동 생성하지 않는다. 준비 데이터로 문서 기능을 검증할 때는 테스트용 데이터임을 검증 기록에서 명시한다.

## 흐름 2: 편집

1. 최신 DocumentView에서 VersionRef와 본문을 편집 초안의 기준으로 잡는다.
2. 저장 시 C04가 소속과 최신 여부를 확인한다. 충돌이면 최신 참조를 반환하고 UI는 초안을 유지한다.
3. 본문이 정확히 같으면 변경 없음으로 종료한다. 변경 시 새 버전·기준 버전 참조·편집 사건·포인터 변경을 준비한다.
4. C09가 기대 최신 참조를 다시 확인하고 함께 저장한다. 성공 후 새 버전으로 상세·버전 목록·이력을 갱신한다.

과거 버전 본문과 이미 저장된 결정/리뷰 대상은 변하지 않는다. 저장 중 오류가 나도 브라우저가 임의로 최신 포인터를 옮기지 않는다.

## 흐름 3: 비교

1. 같은 문서의 왼쪽/오른쪽 VersionRef를 선택하고 정확한 본문을 읽는다.
2. 본문을 줄과 개행 정보로 나눈다. 두 줄열의 동일 부분과 삽입/삭제 구간을 결정하는 줄 단위 diff를 계산한다. 반복 줄로 결과가 여러 개일 때 동일 입력에 동일 표시가 나오도록 결정적인 순서를 사용한다.
3. 동일/삭제/추가와 양쪽 줄 번호, 버전 번호·출처를 반환한다. 변경된 제목은 별도 메타데이터 차이로 표시한다. 본문이 같아도 제목이 다르면 전체 변경 없음으로 표시하지 않는다.
4. 동일 버전·동일 본문, 빈 본문, 마지막 개행 차이를 처리한다. 어떤 경우에도 저장 메서드를 호출하지 않는다.

알고리즘 라이브러리 선택·큰 입력 처리 방식은 NFR/Code Generation에서 결정한다. 이번 단계에서 성능 수치를 약속하지 않는다.

## 흐름 4: 복원

1. 사용자가 과거 버전을 열고 복원 원본과 새 버전 생성 설명을 확인한다.
2. C04.restore가 source 소속과 처리 시작 시 최신을 읽는다. 원본 제목·본문을 복사한 새 버전과 기준/복원 출처를 만든다.
3. 기대 최신 참조를 조건으로 C09.commit한다. 준비 이후 최신이 달라지면 충돌이며 다시 확인하도록 안내한다.
4. 성공 후 새 최신을 연다. 원본과 복원 전 최신이 모두 이력에 남아야 한다.

원본 버전이 이전과 같아도 명시적 복원 행위를 기록한다. 기존 restore(source, actor) 시그니처를 유지한다.

## 흐름 5: AI 결과 저장 전 준비와 후속 연결

1. U2가 자기 실행의 SR 소속과 입력 문맥을 확인한 뒤 정규화된 artifacts를 C04에 전달한다.
2. C04는 SR과 문서 키/ID/본문 및 묶음 중복을 검사하고 변경 준비 시점의 최신 참조를 읽는다.
3. 신규 문서는 새 ID/첫 버전, 기존 문서는 새 버전과 기대 최신 전제를 준비한다. 문서별 생성 사건을 묶는다. 빈 목록은 빈 변경 결과이다.
4. U2는 실행 입력 버전과 현재 상태를 대조하여 늦은 결과 정책을 적용한다. Run·질문·진행 변경과 DocumentChanges를 한 commit으로 확정한다.
5. commit 전제조건 실패는 U2로 반환한다. AI 결과 채택·실패 상태·질문만 있는 정상 결과의 처리는 U2의 기능 설계에서 확정한다.

C04의 준비만으로 문서가 나타나거나 실행 성공 이력이 남아서는 안 된다. U1 단위 검증은 “준비 전후 저장 변화 없음”과 변경 묶음 커밋의 일관성을 확인한다.

## 흐름 6: 본문 없는 사건 조회

U2/U3가 C09 공통 계약으로 응답·결정·리뷰 사건을 저장한다. U1 이력 조회는 본문 변경 유무로 사건을 제외하지 않는다. 문서 필터에서는 versionRefs를 통해 관련 사건을 찾고, SR 전체에서는 버전 없는 사건도 포함한다. 상세 내용과 대상 링크를 통해 어떤 버전에 대한 결정인지 확인한다.

## 저장 경계와 실패

commit은 예상 상태 및 신규 레코드를 포함한 변경 후 참조 그래프를 검증한다. 존재하지 않는 소속, 다른 SR 참조, 중복 logicalKey, 기존 버전 수정, 잘못된 최신 포인터, 사건 대상 불일치는 거절한다. 정상 변경은 SR/문서/버전/사건과 후속 도메인 변경을 함께 공개한다.

전제조건 비교와 쓰기를 분리해 중간 경합을 허용하지 않는다. 실제 원자성 구현 방식은 U1 NFR Design에서 정한다. CLI 실행 동안 저장 트랜잭션을 유지하지 않는다. 요청 응답 유실 등 결과가 불확실한 상황은 재조회로 확인하며 화면에서 확정 성공을 추측하지 않는다.
